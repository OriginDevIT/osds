# OSDS — Decisions

Durable record of architectural decisions and current project state. Written
for a future contributor, or for pasting into a fresh AI session instead of
replaying prior conversations.

**Rule: decisions recorded here are settled.** Reopening one requires new
information, not a fresh opinion. If you disagree, open an issue arguing the
new information — do not relitigate in code or in a chat session.

Last updated: 2026-09-27

---

## 0. The reset

OSDS was first built in TypeScript — a pnpm monorepo of five packages on
Next.js, Kysely and Postgres RLS. That implementation is archived at tag
`v0-node`. It reached 444 passing tests, a working admin login, and a public
site, and it was several weeks from a shippable product.

**The build had diverged from the goal.** The goal is a system that is easy to
deploy and easy to manage, that hosts directory sites. The specification grew
to describe a mature product — premium slot concurrency, dunning windows,
agent escalation triggers — and the implementation chased the specification
rather than the goal. Correctness work on layers nobody could yet use is the
symptom.

The rebuild is Django 5 on Postgres 16, server-rendered, four containers.

**What carries forward:** every product, legal and behavioural decision below.
The specification's rules still bind.

**What is superseded:** everything about how those rules were implemented.
Kysely, the adapter-kit type union, `packages/*` boundaries, Postgres
row-level security as the tenancy mechanism, composite `(tenant_id, id)`
foreign keys, the `osds_app` non-owner role, scrypt session handling, the
`operator_login_attempts` design, and the five admin-surface routing rulings.
They were correct for that implementation. They are not decisions about this
one, and they are in git history if the reasoning is ever needed.

---

## 1. What OSDS is

A self-hostable, multi-tenant directory website system. An operator installs
it, defines one or more directories, populates listings, and sells upgraded
placements. Integrations with CRMs, payment providers, mail and SMS happen
through adapters. The system runs fully with none of them beyond the bundled
defaults.

Apache-2.0. Steward: Origin Development & IT, Inc. Repo: `OriginDevIT/osds`.

## 2. Product and legal posture

Unchanged by the reset. These are why the project exists in this shape.

| Decision                                         | Reasoning                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **No data-source connectors, ever**              | No importers, scrapers, hooks or plugin interfaces for external listing datasets. A system that ships an ingestion connector can be argued to have induced whatever the operator did with the data. A system that provides a database and a form cannot. Population paths are manual entry, CSV upload, owner submission and the write API. Spec §4.1.1. Contributions adding one are declined on sight. |
| **Link to external reviews, never display them** | A "Leave a review on Google" button is a hyperlink — always core, no adapter. Fetching and rendering a provider's ratings is governed by that provider's API terms. Optional adapter, operator's own credentials, operator accepts the terms.                                                                                                                                                            |
| **Consent is a required field**                  | On claim submission and lead capture. Records granted, timestamp, IP, plus a version pointer to an immutable copy of the exact wording shown. Evidentiary, for TCPA. Business phone numbers are not exempt.                                                                                                                                                                                              |
| **Apache-2.0, not AGPL**                         | Maximum adoption, clean for adapter authors, explicit patent grant. Accepted consequence: someone may host a competitor. Relicensing after outside contributions requires every contributor's consent, so this is effectively permanent.                                                                                                                                                                 |
| **Name is OSDS**                                 | Open Source Directory Site. Weak as a brand, precise as a description. Treat as closed.                                                                                                                                                                                                                                                                                                                  |

## 3. Functional decisions

The product rules. Framework-independent, and the reason the rebuild is a
rebuild rather than a restart.

### Tenancy and principals

| Decision                                                        | Reasoning                                                                                                                                                                                                                                                                                                                      |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Multi-tenant schema always; single-directory is a UI toggle** | Every tenant-scoped model carries a tenant reference from the first migration. Retrofitting tenancy is brutal; hiding a selector is trivial.                                                                                                                                                                                   |
| **All tenant data is tenant-specific**                          | No crossover between tenants, including users. A directory user belongs to exactly one tenant.                                                                                                                                                                                                                                 |
| **Two kinds of person**                                         | A **user** owns or seeks to own a listing and belongs to one tenant. An **operator** administers directories, belongs to no tenant, and is one login across the installation. Both have an email address, which is not a reason to merge them. Spec §4.3, §4.4.                                                                |
| **Staff membership is the link**                                | `StaffMembership(operator, tenant, role, status)`. No row means no access to that tenant, whatever the operator holds elsewhere. Admins may therefore be tenant-specific or multi-tenant, with no separate concept for either.                                                                                                 |
| **Two axes, not one ladder**                                    | `is_superadmin` on the operator; `role` on the membership. Creating or suspending a tenant happens outside any tenant, so no membership can authorise it. Everything else is per-tenant.                                                                                                                                       |
| **Superadmin holds no implicit tenant access**                  | They add themselves a membership at a stated role. Unpreventable in principle — anyone who can assign memberships can assign their own. The point is evidence: a grant leaves a row and an event, so hosting-side access to a client's directory is a fact on the record rather than an invisible capability.                  |
| **Five ordered role ranks**                                     | `admin` 4, `manager` 3, `editor` 2, `moderator` 1, `support` 0. Authorization is `rank >= n`. The load-bearing cuts are 3/2 (money and PII) and 2/1 (authority over other people's listings). A capability matrix is the right shape only when roles are configurable, and these are not.                                      |
| **Memberships on an existing operator start pending**           | Otherwise an admin of one tenant can silently attach a directory to the account of an admin of another. A membership minted together with its operator activates on password set — accepting the invitation and the membership are one act.                                                                                    |
| **Invitation never writes to an existing operator row**         | Membership only, and the response is identical whether the email matched. Match-and-update on an invite form is cross-tenant account takeover. A differing response is an oracle for which clients administer other directories on the installation.                                                                           |
| **Tenant admin lives at `/admin` on the tenant's own domain**   | The DNS record and certificate already exist for the public site. A second hostname per tenant is another record the operator must get right before they can log in at all, and a lockout with a DNS error is the worst first experience available.                                                                            |
| **The console is a separate host and is not a tenant**          | Installation-level operations and a directory picker. Every operator reaches it, because accepting a pending invitation happens there. Clicking a tenant opens that tenant's `/admin` and does not carry the session — a cross-host handoff token is a new credential type and the piece most likely to be built subtly wrong. |

### Listings

| Decision                                                                  | Reasoning                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Directories have a type**                                               | Businesses, locations, people, services, software and others. A listing type carries a field schema; type-specific columns would be a rewrite per type. Spec §4.5.                                                                                                                                                                            |
| **Tiers are tenant-configured**                                           | An ordered list with a `rank`. Rank 0 is the fallback tier. Core hardcodes no tier names. A tenant may define no rank-0 tier, which changes downgrade behaviour.                                                                                                                                                                              |
| **Provenance is recorded on every listing**                               | Source, import batch, submitter. Four operational reasons: dedupe across population routes, undo of an import batch, removal that sticks via a suppression key, and trust display on the public page. Not about upstream licensing.                                                                                                           |
| **Removal sticks**                                                        | A deleted listing records a suppression key — normalised name, address and phone hash — that subsequent imports check against, so a removed business does not reappear on the next CSV upload.                                                                                                                                                |
| **Rollback restores updated rows, not just created ones**                 | A batch both creates and updates. Removing only the creations leaves every updated row carrying imported values with no way back. Rollback deletes created rows and re-applies a pre-image to updated ones. Rejected: refusing rollback on any batch that updated a row — most re-imports update, so that refuses the common case. Spec §3.3. |
| **A pre-image is nulled at 90 days, and a nulled batch cannot roll back** | The pre-image is a second copy of personal data — the thing §11.2's nulling rule exists to prevent, and the same reasoning that denies dead letters an exemption. The admin UI states the batch is past its rollback window rather than offering a button that half-works.                                                                    |
| **Rollback writes no suppression key**                                    | The key exists so a business the operator removed does not reappear on the next upload (§4.1.1). A listing removed because the operator undid their own import is not that case, and suppressing it makes the undo permanent. Rollback emits `import.rolled_back` only — no per-listing `listing.deleted`.                                    |
| **Search is core**                                                        | Postgres full-text plus trigram matching, working on a fresh install with no configuration and no extra container. External engines are an optional upgrade. A default deployment must never produce a directory nobody can search.                                                                                                           |
| **Sitemap index from day one**                                            | URL count grows faster than listing count — categories × locations × pagination crosses 50,000 URLs on a 5,000-listing directory. Decide deliberately which facet combinations are indexable.                                                                                                                                                 |
| **`visibility` is a rejected field on `listing.upsert`**                  | It joins `tier` and `status`. Publishing emits `listing.published`, so an upsert that could flip it would either emit an event its outcome table does not name, or bury a publication change inside a JSON Patch. A CSV re-import must never publish a draft as a side effect of touching a phone number. Spec §7.1.                          |
| **`draft ↔ hidden` emits nothing**                                        | Neither state is publicly visible, so nothing became visible or hidden. Only crossing the `published` boundary emits.                                                                                                                                                                                                                         |
| **A listing never changes its type**                                      | An id-matched upsert naming a different `listing_type` is a 422. The type determines the field schema; changing it orphans every custom value.                                                                                                                                                                                                |
| **Removing a field from a type orphans its values**                       | No sweep, no block. The values stay in `custom_fields`, invisible, and re-adding the key restores them. A destructive data migration triggered by an admin unchecking a box is worse than dead JSON keys.                                                                                                                                     |
| **A type's `key` is frozen after creation; `path_segment` is not**        | `key` appears in patch pointers and event payloads that adapters route on. `path_segment` is editable and writes a `PathRedirect`, because the operator will get the URL wrong the first time and the alternative is recreating the type.                                                                                                     |
| **Category paths are one level in the URL**                               | Regardless of tree depth. `/plumbers/hoffman-plumbing` even where `plumbers` sits under `trades` for browsing. Deep nesting multiplies indexable paths for no gain, and slug uniqueness is already per `(tenant, listing_type)`.                                                                                                              |

### Claims

| Decision                                                      | Reasoning                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Manual admin review is the default and always available**   | Records the method used, who verified, when, and mandatory notes — an admin who cannot articulate how they verified has not verified.                                                                                                                                                                                                                                                |
| **Email OTP ships alongside manual at launch**                | Phone OTP, postcard and Google Business Profile OAuth are planned and must not be designed out. Phone OTP is the eventual workhorse. GBP requires a separate approved Google Cloud project per self-hoster, so it is optional and never default.                                                                                                                                     |
| **Core computes code expiry, never the caller**               | A lifetime is a rule. Tenant-configurable within bounds core enforces; a value outside the bounds is rejected at configuration time, not silently clamped at use.                                                                                                                                                                                                                    |
| **Notify every existing contact channel on successful claim** | Catches what verification misses, costs almost nothing.                                                                                                                                                                                                                                                                                                                              |
| **Mask contact details in the verification UI**               | Otherwise the claim flow is a phone-number disclosure endpoint for every listing on the site.                                                                                                                                                                                                                                                                                        |
| **Disputes go to moderation, never auto-transfer**            | A second claim on a claimed listing opens a moderation item. Verification alone never moves ownership away from a sitting owner.                                                                                                                                                                                                                                                     |
| **The verification code is hashed, never stored or emitted**  | `claim.verification_started` carries `method`, `expires_at` and a masked destination only. The bundled `webhook` adapter is default-enabled, so a code in the payload is a live credential POSTed to an operator-supplied URL and retained for 90 days by §11.2. Core compares a hash; the plaintext exists only in the message sent. Spec §9.6.                                     |
| **`domain_email` matches the listing's website host**         | Leading `www.` stripped, nothing else. A subdomain website requires a subdomain email. No website, no match, or a platform page → manual review with the operator notified. A claimant who cannot receive mail at the business's own domain has not demonstrated what the method claims. Rejected: matching `contact.email`, which only requires reading the public page. Spec §9.6. |
| **Attempt limits are core's, not tenant-configurable**        | Five wrong codes kill the code and open a 15-minute cooldown on `(listing, email)`; three cooldowns lock the pair to manual with a moderation item. An operator raising a brute-force ceiling on a form field is not making a security decision knowingly — the reasoning §9.5 already applies to lifetimes. Spec §9.6.                                                              |
| **Three rejections block that email on that listing**         | A rejected claimant may resubmit; §9.3's mandatory notes are what tell them what was missing. Three blocks the pair, opens a moderation item, and only an operator unblocks. Scope is the listing, never the tenant — someone rejected on one business may own another, and a tenant-wide email block is a support call. The rejection and cooldown counters never reset each other. |
| **An owner signs in with an emailed link, never a password**  | 12-hour link, session expiring after 12 hours idle. No credential on a user row, so no reset flow and no lockout policy. §4.3 warns that reusing a user row on an email match stops being safe once a stored credential outlives the verification that justified it; a link re-proves mailbox control on every entry, which closes that without a second credential store.           |

### Entitlements and money

| Decision                                      | Reasoning                                                                                                                                                                                                                     |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Core owns entitlement; adapters own money** | Payment adapters report outcomes. Core decides tier consequences. **There is no command that sets a listing's tier** — with a settable tier, any adapter becomes the source of truth.                                         |
| **Payments ship at launch**                   | Comps and paid entitlements both. The full lifecycle seam — status, period end, payment reference — is built once rather than retrofitted.                                                                                    |
| Dunning window                                | 14 days. Most failed payments are involuntary — expired cards, not churn.                                                                                                                                                     |
| Public display during dunning                 | Full perks retained. Demoting someone whose card expired is invisible to them and loses customers who intended to pay.                                                                                                        |
| Grace after dunning                           | 30 days, downgraded, restore path open.                                                                                                                                                                                       |
| At expiry                                     | Downgrade to rank 0, **never unpublish**. Unpublishing destroys an indexed page and reads as punitive. Exception: a tenant with no rank-0 tier hides the listing, and the admin UI must say so at the point of configuration. |
| Cancellation                                  | At period end, skips grace. They chose to leave; grace exists for involuntary failure.                                                                                                                                        |
| Refund                                        | Immediate downgrade.                                                                                                                                                                                                          |
| Data collected while paid                     | Retained, access gated. Never delete leads or reviews on downgrade. "You received 34 leads while on Featured" is the best renewal prompt available.                                                                           |
| Trials                                        | Card required up front. Off by default on slot-backed tiers.                                                                                                                                                                  |
| Comps                                         | Consume sellable slot capacity. Anything else makes capacity numbers lie.                                                                                                                                                     |
| Proration                                     | The payment adapter computes it; core receives a new period end. Keeps fiddly arithmetic in the system that already solves it.                                                                                                |

### Slots — first post-launch addition

Not built for launch. Rotation of unsold placements and locked capacity are
separable and may land earlier.

| Decision         | Reasoning                                                                                                                                                                                          |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Waitlist notice  | T-10 days, worded "_may_ become available". The incumbent holds right of first refusal until the moment of expiry. Overstating availability generates complaints.                                  |
| Unsold slot fill | Locked → default featured → random rotation. Rotation means a new directory never shows empty slots, and free listings get intermittent premium placement — the best upgrade pitch available.      |
| Allocation       | One row per capacity unit, locked with `FOR UPDATE SKIP LOCKED`. The row _is_ the lock. Over-sell is impossible by construction. Rejected: counter columns, advisory locks, materialize-on-demand. |

### Adapters

| Decision                                                       | Reasoning                                                                                                                                                                                                                                                        |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Core never imports adapter code**                            | No vendor name appears in core. Core knows capability names only. This is what keeps any single vendor from becoming a dependency of the project.                                                                                                                |
| **Adapters never write core listings directly**                | They send commands; core validates, applies and emits. An adapter that writes the database bypasses event emission and the command log.                                                                                                                          |
| **Postgres outbox, no message broker**                         | Events written in the same transaction as the state change, drained by a worker. Zero extra containers keeps one-click self-hosting viable. A directory does not generate broker-scale traffic.                                                                  |
| **Delivery is at-least-once**                                  | Adapters dedupe on event id. Ordering is guaranteed per subject, never globally.                                                                                                                                                                                 |
| **Loop prevention is structural**                              | Core stamps the originating adapter id on the resulting event; an adapter ignores any event it originated.                                                                                                                                                       |
| **PII is opt-in per adapter**                                  | Redaction is the default.                                                                                                                                                                                                                                        |
| **Agent restrictions are scopes, not prompts**                 | No entitlement commands, no compliance commands, no deletion, mandatory transcript reference, global kill switch. A restriction that exists only in prompt text is not implemented. Agents are post-launch; the scope model must not be designed out.            |
| **Three logs, three retentions**                               | Event log (envelope forever, payload nulled at 90 days), command log (forever, including rejected and blocked), access log (2 years, separate store). The payload is a second copy of personal data — the copy people forget when processing a deletion request. |
| **The command log is written outside the command transaction** | Recorded before the transaction opens, concluded after it settles. A log written inside the transaction it is logging disappears when that transaction rolls back — which is exactly the case the log exists for. A concluded row is never rewritten.            |

### Deployment

| Decision                                  | Reasoning                                                                                                                                                                                         |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **First-run wizard, never config files**  | The target operator can rent a server but should never edit YAML to set an admin password. The wizard sets the superadmin, the first tenant, its domain, storage, SMTP and enabled claim methods. |
| **The wizard assists with DNS**           | It shows the record to create and verifies it, rather than assuming the operator knows. A lockout behind a DNS error is the worst first experience available.                                     |
| **Setup token printed to container logs** | Plus the route disappearing once an operator exists. The gap between bringing the stack up and opening a browser is a real window on a public IP, and the count check alone does not cover it.    |
| **Four containers**                       | App, worker, Postgres, object storage — the last two replaceable by managed services through configuration alone. A fifth container to support any single feature is a decision, not a detail.    |

## 4. Implementation decisions — Django

New. These are decisions about the current implementation only.

| Decision                                                                         | Reasoning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Django 5, Postgres 16, templates plus HTMX**                                   | Server-rendered fits a directory. No SPA framework, no build step for the public site.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Row-level tenancy via a scoped default manager**, not RLS or schema-per-tenant | Schema-per-tenant makes the cross-tenant console query N queries. Postgres RLS remains the correct defence in depth and is planned, but app-level scoping ships first. **The consequence is accepted and named: one unscoped query is a cross-tenant leak.** A test asserts every tenant-scoped model's default manager is the scoped one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Writes go through a service layer**                                            | The ORM does not emit events or write the command log. Django admin is disabled for tenant data for the same reason — it writes tables directly. Django admin is used for the installation console only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **The console admin writes through services, never `save_model`** (#146)         | Registering `Tenant`, `Operator` and `StaffMembership` in the console admin is consistent with "Django admin is disabled for tenant data" — these are principal and structural models, not tenant data. But a raw admin save emits nothing, so each goes through its service function: `Tenant` emits `tenant.created`, `StaffMembership` emits `staff.invited`. **`Operator` creation emits no event and writes the command log only.** An operator belongs to no tenant, and §4.4 already reasons that installation-scoped acts fit neither envelope arm — `OsdsAnyEvent` is `OsdsEvent \| TenantEvent`, and a tenant block would be a lie. `command_log` takes a null `tenant_id` for exactly this case (§11.2), which is the audit trail that matters. An `operator.*` namespace would mean widening the envelope union and is a spec change, not an implementation decision. **This surface emits `staff.invited` only** — `staff.accepted` fires when a pending membership is accepted, and there is no set-password acceptance view (#163). |
| **The console admin bypasses the changeform entirely, not just `save_model`**    | `ModelAdmin.changeform_view` wraps `_changeform_view` in `transaction.atomic`, so routing a write through the built-in add form — even with a custom `ModelForm` — puts the command log inside the transaction it exists to survive (§11.2). `add_view` is overridden outright and never calls `super()`, which means re-supplying the `csrf_protect` decorator and the explicit `has_add_permission` check the bypassed view normally provides. Forms are plain `forms.Form`, never `ModelForm`: a `ModelForm` carries an `instance` and a `.save()`. `save_model` and `save_related` raise `NotImplementedError` so a later permission change cannot silently reintroduce an ORM write. The acting operator is `request.user`, passed to the service as an explicit kwarg — never a ContextVar, since no tenant is resolved on the console host.                                                                                                                                                                                                 |
| **No Celery, no Redis, no broker**                                               | Celery has no supported Postgres broker; the SQLAlchemy and Django transports were dropped. Adding it means a fifth container and breaks one-click self-hosting. Scheduled work — dunning transitions, grace expiry, term expiry, renewal notices, payload nulling, sitemap regeneration — runs in the worker's tick loop. If a real queue abstraction is later needed it must use the database as its broker.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Long work is queued, never in-request**                                        | CSV import, media processing and mail run on the worker. A several-hundred-row import times out a browser request. The upload stores the file and creates a batch row; the worker processes it. **One accepted exception: import rollback runs in-request (#192)** — it is one transaction over the rows of a single batch, not an unbounded loop, and queueing it would mean a second status surface for an operation the operator is watching. Named here because an unrecorded exception is how the rule erodes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Mail leaves through an `OutboundMessage` row, not the outbox**                 | Core writes the message in the same transaction as the state change that caused it; the worker drains it and calls whatever is registered under the capability name `email.send`. Core imports no vendor code — `osds/adapters.py` is the seam it already was. The outbox is the wrong carrier: a verification code in an event payload is a credential handed to the default-enabled `webhook` adapter and kept 90 days. A minimal bundled `smtp` sender on stdlib `smtplib` against the wizard's SMTP settings is **pulled forward from block 5** so email OTP can ship in block 3; the block-5 adapter replaces the sender without core changing. No new dependency, no fifth container.                                                                                                                                                                                                                                                                                                                                                        |
| **No `post_save` audit package**                                                 | `django-auditlog` and `django-simple-history` record what succeeded, inside the transaction that succeeded. The command log's purpose is rejected and blocked attempts, written outside the command transaction. A signal-based package structurally cannot see the rows that matter most. Both logs are hand-rolled.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Storage is per-tenant, resolved at runtime**                                   | `django-storages` reads settings at import time, and wizard-entered credentials live in the database. A thin backend resolves the target from tenant configuration per request. Local disk is the default; S3, Azure and GCP are configurable in the wizard.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Geo is `lat`/`lon` plus raw-SQL distance**                                     | GeoDjango needs GDAL and GEOS binaries the development machine does not have. Radius search works without them. PostGIS is planned server-side.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **A devcontainer is planned, not deferred indefinitely**                         | Anything that genuinely requires Linux-only native binaries pulls it forward immediately.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Event names live in a constants module**                                       | With a test asserting every emitted type appears in it. This replaces the TypeScript union that made a typo a compile error.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Settings raise at import for required secrets**                                | `DJANGO_SECRET_KEY`, `OSDS_SECRET_KEY` and `DATABASE_URL` have no defaults. A default encryption key in a public repository means an operator who forgets the variable encrypts their storage and mail credentials with a value anyone can read. `DEBUG` defaults to False.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **`ALLOWED_HOSTS` is `['*']`; the middleware is the host gate**                  | Tenant domains are added at runtime and cannot be enumerated statically. `TenantResolutionMiddleware` runs **before** `SecurityMiddleware` — with `ALLOWED_HOSTS` permissive, nothing validates the Host header until it does, and an SSL redirect built from an unvalidated host is a redirect-poisoning primitive.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **`ATOMIC_REQUESTS` stays False**                                                | `upsert_listing` raises when a caller already has a transaction open, because the command log must commit independently of the command it logs (§11.2). Request-wrapped transactions would break every write path. Pinned explicitly rather than relying on the default.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Migrations run as the database owner**                                         | `CREATE EXTENSION pg_trgm` and `CREATE INDEX` need the owner role. The container entrypoint migrates with `DATABASE_URL_ADMIN`; the app runs on the least-privilege `DATABASE_URL`. Deploy wiring, not a settings branch.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **No object-storage container at launch; media is a named volume** (#178, #150) | §3 names four containers, the last being object storage. Storage is local disk only (#150): `get_tenant_storage` has no S3 path, and adding one needs `boto3`, a human-gated dependency. A MinIO container would run with nothing attached while the wizard's S3 option still raised the deferred-feature error. At launch the fourth container is therefore the `osds-media` named volume, mounted at `OSDS_MEDIA_ROOT` in **both** `osds-app` and `osds-worker` — the worker reads uploaded CSVs from it. When the S3 backend ships, the compose file gains a `minio` service in the same PR. Spec §13 still lists `minio`; that is a spec edit and is raised separately. |
| **Secrets are generated at first boot into a named volume, not a config file** (#178) | The target operator never edits a config file (§3). On first boot the `postgres` container — the first up, and the only one needing a secret before anything else — writes `db_owner_password`, `db_app_password`, `django_secret_key` and `osds_secret_key` into the `osds-secrets` volume, once, as hex. Postgres reads its password through `POSTGRES_PASSWORD_FILE`; the app entrypoint exports the others **only for a variable not already set**, so a `.env` override wins and a truly unset variable still makes `settings.py` raise. `.env` is optional overrides only. No one-shot fifth container. The owner URL exists only in the entrypoint's shell and is unset before gunicorn or the worker starts. **The consequence is accepted and named: losing `osds-secrets` loses `osds_secret_key`, which encrypts every credential stored through the wizard, and nothing else can decrypt them.** The README says so. |
| **A migration that imports live code names a frozen function**                   | 0004's backfill calls `recompute_search_vector_v1`, documented as frozen migration history. CI migrates from zero, so the loop body never runs and behaviour drift is undetectable. The naming convention makes such an edit an obvious violation rather than an innocent refactor.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Vendored front-end assets, never a CDN**                                       | htmx is committed with a provenance header. The admin runs on an authenticated tenant session; a CDN load is a third-party script on that session and leaks the tenant's domain on every page.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Authentication writes to no log**                                              | Spec §11.2 defines three logs: events, commands, access. A session is none of them — no command verb, no outbox event, no view or export of data. `last_login` is the only record kept. The Node-era `operator_login_attempts` table is superseded (§0) and is not reintroduced under another name. Login auditing means a new `AccessLog` action argued in an issue, not a fourth log.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **`SECURE_PROXY_SSL_HEADER` is set; `CSRF_TRUSTED_ORIGINS` is not**              | Tenant domains are runtime rows and cannot be enumerated in settings — the same constraint that produced `ALLOWED_HOSTS = ['*']`. Login POSTs are same-origin, so Django's host comparison suffices, but only if Django knows the request scheme. Behind TLS termination it does not, the origin check compares `https` against `http`, and every login POST is a 403. Safe only because the deployment proxy is required to strip a client-supplied `X-Forwarded-Proto`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **The first-run wizard relaxes cookie `Secure`**                                 | Served over plain http before any TLS, the wizard's `Secure` session and CSRF cookies are dropped by the browser, so first boot cannot pass CSRF or hold its unlock flag. `SetupCookieSecurityMiddleware` strips `Secure` from those two on `/setup/` responses while `InstallSetup.completed_at` is null. The gate is that route plus setup being incomplete, with no `request.is_secure()` check, and self-destructs when completion stops the setup URLconf resolving.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Per-adapter delivery state is its own table** (#171)                           | `OutboxDelivery`, one row per `(event, adapter_id)`. §8.2 gives each adapter an independent attempt count and backoff, and one status column on `OutboxEvent` holds one consumer's progress. `OutboxEvent.status` therefore means **fanned out**, not delivered. The `tenant` FK is nullable because `tenant.*` events carry no tenant block — and **a nullable tenant is not the §11.2 `command_log` exception**: that exception is bounded and argued, and taking it by analogy is how the tenancy invariant rots. `OutboxDelivery` carries the tenant-scoped default manager and `all_tenants` like any other tenant-scoped model. `subject` is denormalised onto the row so the head-of-line ordering check never joins `outbox_events` on the claim path.                                                                                                                                                                                                                                                                                     |
| **The drain holds no row lock across the handler**                               | A short transaction takes `FOR UPDATE SKIP LOCKED`, pushes `next_attempt_at` to a 90-second visibility deadline and commits; the handler runs unlocked; the result lands in a second short transaction. A 30-second handler (§8.2) inside `FOR UPDATE` would pin a connection and a transaction for its whole attempt. A crashed worker's delivery becomes claimable again when the deadline passes. **`_record` is therefore a conditional update keyed on the deadline the claim stamped:** a handler that hangs past 90 seconds has its row re-claimed and finished by a later pass, and its eventual write must not land. At-least-once covers a duplicate delivery; it does not cover a double-incremented `attempt` or a stale `retried` overwriting a `delivered`. `attempt` increments only after the handler returns, and `BaseException` propagates untouched — a `KeyboardInterrupt` mid-handler is a shutdown, not a failed attempt.                                                                                                   |
| **Dead letters are not exempt from payload nulling**                             | A dead `OutboxDelivery` is replayable from the admin (§8.2), but its event's `data` is nulled at 90 days like every other payload (§11.2). Exempting dead letters rebuilds the shadow copy of personal data that the nulling rule exists to prevent, and a 90-day-old dead letter is not worth replaying. Replay older than that reconstructs from current state.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

## §4.3 — Outbound mail

New subsection. Claims PR 2 rulings.

| Decision | Reasoning |
| --- | --- |
| **`OutboundMessage` is one table with delivery state on the row** | One consumer and no fan-out, so a per-consumer table like `OutboxDelivery` would always hold exactly one row. The drain mechanics are copied exactly: a `SKIP LOCKED` claim, a 90-second visibility deadline, and a result recorded only if the stamped deadline still matches. The concurrency hazards do not depend on consumer count. Statuses `pending \| sent \| dead \| expired`; §8.2 backoff. |
| **`expires_at` is required and bounds every message** | The producer sets it to the code's or link's own expiry; a notice with no natural deadline gets one from its producer. Past it, the drain marks the row `expired` and never sends. A code delivered after it died reads as live and burns §9.6 attempts. `expired` tells the operator SMTP was down long enough to kill a message, which `dead` does not. Originally nullable: with no attempt ceiling, a null deadline let a retryable error such as a wrong SMTP password retry forever without ever nulling the body. Rejected: §8.2's 12-attempt ceiling, which dead-letters a security notice after about 68 minutes of misconfiguration. `dead` is reserved for recipient refusal. |
| **`body_text` is nulled on terminal state; `to_address` at 90 days** | The body holds the plaintext code, and §9.6 says the plaintext exists only in the message sent. It is nulled in the same write that sets `sent`, `dead` or `expired`. The address is kept for delivery debugging and nulled at 90 days per §11.2 by the daily `outbound_address_retention` tick job (#213, §4.7), and only on a terminal row. `subject` is template text and stays. |
| **`OutboundMessage.tenant` is non-null** | It fails the §11.2 `command_log` exception on two of its three conditions: it is a pending state change the drain reads back and updates. Operator invitation mail is installation-scoped and is #163's design problem. |
| **Capabilities resolve through `capability_provider(name)` in `osds/adapters.py`** | Beside the event subscribers. One provider per capability; a second registration raises. The `smtp` sender lives in `adapters/smtp/` and is wired by the `osds` bootstrap (§8.6). A test asserts nothing under `directory/`, `tenants/`, `billing/` or `audit/` imports `adapters`. Rejected: a separate `osds/capabilities.py`, because two registry modules drift. |
| **Unavailable mail leaves the row pending** | With no provider registered, or empty SMTP settings or `from_email`, no attempt is consumed and no backoff applies. The row is rechecked on a fixed 60-second interval, and `expires_at` governs. A pass whose only mail activity was unconfigured rows is not work and idles: counting it made the worker busy-loop with no wait, caught in the browser pass. The drain logs one aggregate line per pass at WARNING, because the project ships no `LOGGING` configuration and an INFO record is discarded; a real configuration belongs with #179. Treating unavailable mail as a failure would dead-letter every message queued before the operator configured mail. This is the state #121's skip action produces. |
| **#121 follows PR 2 as its own PR** | Wizard UI and a credentials surface, both human-gated. The drain needs nothing from it once unconfigured mail is a defined state. |
| **The mail drain runs every worker pass, not as a tick job** | Beside the outbox drain, on the 1-second idle poll, with no NOTIFY. A user-facing code does not belong on a tick period, and a drain does not need the tick registry. |
| **`enqueue` raises outside an atomic block** | The mail ruling's guarantee is atomicity with the causing state change: a stored hash with no message, or a message with no hash, is a broken claim. The inverse of `upsert_listing`'s guard, enforced for the same reason. |
| **Sending emits no event and writes no command log** | §3.3 has no mail namespace and PR 2 does not invent one. The causing command already emits and logs. Delivery state is on the row. An adapter needing delivery events is a spec addition argued in an issue. |
| **The bundled sender is stdlib only** | `smtplib` and `email.message.EmailMessage`, plain text. Settings are read per send from the database, with credentials via `Secret`. 30-second timeout (§8.2). TLS per `smtp.security` (§4.5), never downgraded. Logs `message_id` and the error class only: §8.3 forbids logging contact values, and #179's redaction does not exist yet. A recipient 5xx is permanent and goes to `dead`; connection errors and 4xx retry. Rejected: `django.core.mail`, which contradicts the settled stdlib wording. |
| **Local mail is tested against Mailpit, a dev-only container** | Python 3.12 removed `smtpd`, and `aiosmtpd` would be a new dependency. Mailpit is never in `requirements.txt`, the compose file or the runtime. |

## §4.4 — Claim verification

New subsection. Claims PR 3 rulings, `domain_email` only.

| Decision | Reasoning |
| --- | --- |
| **A correct code records success and stops** | It sets `Claim.verified_at`, clears `code_hash` and concludes `claim.verify` as `applied`. Status stays `pending_verification`, and no success event is emitted. PR 4 moves approval into the same transaction: `claim.approved` on an unowned listing, dispute on an owned one, and any claim already carrying `verified_at` is consumed. Rejected: emitting `claim.approved` without the owner write and the notice, which breaks #48 and §9.4. Rejected: absorbing approval into PR 3, which makes it two concerns. The window between the merges exists only on dev databases. Nothing in PR 3 moves ownership, including away from a sitting owner. |
| **Verification starts inside `claim.submit`; resend and restart go through `claim.start_verification`** | Both call one internal start function. It generates the code, stores the hash, sets `expires_at`, calls `enqueue` and emits `claim.verification_started`, in the caller's transaction. The common case needs no second click. The restart that §9.6's cooldown forces reuses the same generator and hash path. |
| **The verified address is the claimant's submitted email** | It is the address `DirectoryUser` is matched on, and where the owner's sign-in link will go. Verifying a different address would leave the user row with an address nobody proved, which is the case §4.3 warns makes row reuse unsafe. |
| **An ineligible `domain_email` claim flips to `manual` in the service** | Ineligible means no website, a platform website, or an address not at the website's host. This follows §9.6 as written. §4.5 adds a fourth reason, mail unavailable. `claim.submitted` carries `method: manual`, no code is produced, and the requested method survives in the command-log payload. `claim.start_verification` re-checks and flips too, because an import can change the website. `ClaimForm` offers `domain_email` only for an eligible listing and shows the required `@domain`, which the masked destination already discloses. Rejected: a form error, which contradicts §9.6. |
| **Platform hosts are a fixed core list** | These are social, marketplace and free-hosted-site registrable domains, matched on equality or subdomain. They are not tenant-configurable, for §9.6's reasoning on limits. Both hosts are normalized before comparison: lowercase, IDNA to ASCII, port and trailing dot stripped, and exactly one leading `www.` stripped from the website host only. A test pins a sample of the list. |
| **Operator notification ships with the review queue** | §9.6's "operator notified" ships in PR 4 with the manual-review surface, so the notice links to something actionable. It covers every claim entering manual review, flipped or chosen. #218. |
| **The code is six digits under a keyed hash** | `secrets.randbelow(10**6)`, zero-padded. Five entries per window and three windows make 15 guesses per pair, about 1 in 67,000. `code_hash` is Django `salted_hmac` with salt `osds.claim.verification_code` over `f"{claim.public_id}:{code}"`, sha256, compared with `hmac.compare_digest`. A plain digest of a six-digit code reverses from a dump in under a second. Rejected: PBKDF2, whose slowness buys nothing once the key defeats offline attack. Rejected: keying from `OSDS_SECRET_KEY`, which guards stored credentials and is heavy to rotate. |
| **TTL is read from §9.5's configuration shape** | `settings["claim_verification"]["ttl"]["domain_email_minutes"]`, 1440 when absent. The code's `expires_at` is the `expires_at` passed to `enqueue`. |
| **§9.5 bounds are a core constant validated at configuration** | Bounds for all three code methods live in one constant. They are validated by `update_tenant_settings` for the `claim_verification` key, and an out-of-bounds or wrongly typed value is rejected. `ClaimsForm` reads its limits from the constant. At use, a stored value outside the bounds, which only direct SQL can produce, falls back to the method default with a WARNING. That is a default, not a clamp. #209. |
| **Code entry is bound only by the claim ID** | `/claim/<claim public_id>/verify/`. The code is the authenticator, and attempts are counted per pair, not per browser. A session binding strands a claimant who switches device and stops no one, because the attacker who can lock a pair filed the claim and holds every URL. The email carries the code and a plain link to that page. The code is never in a URL, because mail scanners follow links. |
| **`claim.verify` logs the claim ID only** | The payload is `{"claim_id"}`, never the entered code or its hash. The actor is the claimant's user `public_id`, never an email (#219). A wrong code concludes `applied` with `result_event_id` set to its `claim.verification_failed` event, because it changes state. `rejected` is reserved for guard refusals that change nothing. `claim.start_verification` uses the same payload and actor shape. |
| **The counters live on a per-`(listing, claimant)` guard row** | The row is keyed on the `DirectoryUser` FK, so no second copy of the address is stored. Fields: `wrong_entries`, `cooldowns`, `cooldown_until`, `verification_locked_at`, `rejections`, `claim_blocked_at`, `last_code_sent_at`, `codes_sent_window_start`, `codes_sent_in_window`. It is taken `select_for_update` on every entry. A count on the code would be reset by a resend, a route around the limit exactly like a rejection resetting it. The fifth wrong entry clears `code_hash`, opens a 15-minute cooldown, increments `cooldowns` and zeroes `wrong_entries`. The third cooldown sets `verification_locked_at` and flips the claim to `manual`. `submit` refuses a pair with `claim_blocked_at` set; nothing writes `rejections` until PR 4. `Claim.attempts` remains a per-claim tally for the reviewer. |
| **The claimant is told exactly where they stand** | Tries left, when a cooldown ends, how many cooldowns remain before manual review, and when the claim has gone to manual. The limits are published and the state is the claimant's own, so specificity discloses nothing. A generic message turns a typo into a support call. Times are shown in the tenant's zone if stored, otherwise UTC. |
| **An expired code's entry changes nothing** | `expires_at` decides expiry, so `code_hash` stays until the next start overwrites it. The entry is a `rejected` refusal and consumes no attempt, because a dead code cannot be guessed. |
| **The lock's moderation item and the unlock ship in PR 4** | PR 3 sets `verification_locked_at` and flips to `manual`. `ModerationItem` is designed in PR 4 around disputes, its representative producer, with the lock as a second `item_type`. The operator unlock never touches `rejections` or `claim_blocked_at`. Rejected: emitting `moderation.queued` for an item that does not exist. #220. |
| **A resend supersedes the prior code** | Only the latest hash is valid, and `expires_at` restarts. The prior `OutboundMessage`, if still `pending`, has `expires_at` set to now in the same transaction, so a dead code is never sent after an outage. The link is a nullable `Claim.code_message`. Superseding grants no guesses, because the counters are on the pair. |
| **Sends are capped per pair, core-fixed** | At least 60 seconds between sends, and at most 5 per rolling 24 hours, counting the code at `submit`. Disabled during a cooldown and after the lock. Otherwise anyone can name an address and flood it from the operator's SMTP. Per-IP limiting (#210) does not protect the recipient, because IPs rotate and the pair does not. |
| **Verification events** | `claim.verification_started` on every start carries `claim`, `method`, `expires_at` and the masked `destination`. `claim.verification_failed` on every wrong entry and on a post-submit flip carries the after-state `claim`, the failed `method`, and `reason` (`wrong_code`, `cooldown`, `locked` or `ineligible`). It also carries `attempt` (1 to 5 in the pair's window) and `cooldowns`, both null for `ineligible`. Guard refusals emit nothing. |
| **The message: kind, subject, body** | `kind` is `claim.verification_code`. The subject is `Your verification code for {listing name}` and never contains the code, because `subject` survives body nulling. The plain-text body carries the site name, the listing name, the code, the expiry, "only the most recent code works", and the absolute verify URL. It carries no claimant-supplied text, since anyone can name another person's address and would otherwise write into mail from the operator's domain. |
| **#210 and #212 stay separate** | #210 needs its own ruling on trusted client IP behind the proxy, and rate-limit storage without Redis. #212 concerns `claim.submit`'s existing branches. PR 3 renders and tests its own new refusals. |
| **Claimant-facing times are UTC** | No time zone is stored on `Tenant`, so §4.4's "otherwise UTC" is the branch that runs. Nothing else needs a zone field yet. |
| **No absolute base, no link line** | When `has_absolute_base(tenant)` is false, the message omits the verify link rather than carrying a relative path that no mail client can follow. The claimant is already on the verify page: submit redirects there whenever the method is `domain_email`. |
| **Submit during a cooldown or a spent send cap still creates the claim** | No code and no message are sent. The verify page shows when a send becomes possible. The inner start function returns "not sent" and never raises for these, so `claim.submit` concludes `applied`; only the `claim.start_verification` wrapper concludes them `rejected`. A lock at submit flips the claim to `manual`, and a blocked pair is rejected. |
| **Resend is its own POST-only route** | `claim/<claim id>/verify/resend/`, so each view calls exactly one command. |
| **Verify and start lock the guard row, then the claim, before any check** | Found in plan review: checking claim state before taking the lock let a parallel correct entry and wrong entry both pass on stale state. Verify refuses in the order status, method, verified, locked, cooldown, no active code, expired, so the reason always names the real state. |
| **The submitted page names the real reason for a flip** | The reasons are no eligible website, address not at `@host`, a locked pair, and, from §4.5, email verification unavailable. Found in the browser pass: a locked pair was being reported as an address mismatch. |

## §4.5 — Mail configuration

New subsection. #121 rulings.

| Decision | Reasoning |
| --- | --- |
| **#121 ships as one PR** | The mail settings form, the TLS mode, the from-address pre-fill, `available(tenant)`, the unconfigured-mail banner, the wizard's Skip action and the `domain_email` fallback land together. Skip without a settings page would ship a state whose only exit is the Django shell, and a settings page without the fallback would let a claimant be told a code was sent that never will be. An earlier ruling split this into two PRs; it is superseded. The storage step needs nothing: `local` is already a one-field default. Moving `smtp.username` and `storage.access_key` into `Secret` is #224; recording settings changes in the command log is #225. |
| **Mail settings live at `/admin/settings/mail/`, editable by the highest tenant role** | The same form as the wizard, written through `update_tenant_settings` and `set_secret`. It is a credentials surface, so the top role only. A blank password keeps the stored `Secret`, an explicit checkbox removes it, and the value is never rendered back. |
| **TLS mode is `smtp.security`: `none`, `starttls` or `tls`** | It replaces the `use_tls` boolean, which could not express implicit TLS on port 465. A data migration maps `true` to `starttls` and `false` to `none`; it is plain dict manipulation, idempotent, and imports no live code. The sender reads only the new key, and `tls` uses `smtplib.SMTP_SSL`. The port is pre-filled with 587; the help text gives 465 for `tls` and 25 for `none`. Rejected: a read-time fallback to `use_tls`, which keeps two shapes forever. |
| **Both TLS modes verify the certificate; credentials never go in the clear** | `starttls()` and `SMTP_SSL` both take `ssl.create_default_context()`. A bare `starttls()` uses the stdlib's unverified context, so certificates were not being checked. A username with `security` `none` is rejected by the form and by `update_tenant_settings`, and the sender treats it as unconfigured rather than authenticate in the clear. |
| **The from address is a pre-fill, not a send-time default** | The form's initial value is `noreply@` plus `primary_domain` verbatim, blank when the tenant has no domain. An empty stored `from_email` stays unconfigured. The mangled address in #121's first comment was typed or autofilled; no code produced it. |
| **Mail availability is one predicate on the capability** | An `email.send` provider exposes `available(tenant) -> bool`, meaning configured, not reachable. The sender's own unconfigured check calls it, so the drain's `CapabilityUnconfigured` path, the admin banner and `claim.submit` agree, and claim eligibility, the banner and the drain never read `settings["smtp"]`. Core's configuration surface -- the form, the settings validator and `setup_state` -- does read and write that key, as it does `storage` and `claim_verification`; it never uses it to decide whether mail can be sent. Core's helper returns false when no provider is registered. Transient outages still queue and retry. |
| **`domain_email` flips to `manual` when mail is unavailable** | A fourth ineligibility reason beside §4.4's three, checked before create through the same path and re-checked by `claim.start_verification`. The submitted page says email verification is unavailable. Rejected: allowing it, which tells the claimant a code was sent that never will be and burns their send cap on resends. Rejected: refusing it at configuration, which makes core read `settings["smtp"]`, misses an unregistered provider, and breaks when block 5 replaces the sender. |
| **The settings page has no superadmin bypass** | It is gated by `tenant_admin_required` at the top role and nothing else. `is_superadmin` is installation-scope authorization and no other `/admin/` view honours it, so one credentials page doing so would be a precedent set by accident. A superadmin with no membership on a tenant gets the same 404 as anyone else; the console can mint one. Rejected: the "plus superadmin" this section first recorded. |
| **Migrating `use_tls` can leave a tenant unconfigured** | A tenant that had a username and `use_tls` false becomes `none` plus a username, which the sender treats as unavailable, so its mail stops and the banner appears until an admin picks STARTTLS or TLS. It previously sent plain AUTH. The migration prints how many tenants this affects and emits no `tenant.settings_changed`. `starttls` now verifies certificates, so a self-signed relay also fails, with a retried error and no opt-out. |
| **The stored password is never sent to a new host** | A host change with a username set and a blank password is a form error and an `InvalidTenantSettings` from `update_mail_settings`: "re-enter the password". Removing the password with the checkbox is accepted, since nothing is then sent. A stored secret with no stored host, which Skip can leave behind, counts as a change. The check lives in the service and form, not in `_validate_smtp`, because a value-only validator sees neither the stored host nor whether a password arrived. Skip deletes the stored password. |
| **Every flip to `manual` clears the code and expires the pending message** | All reasons: `code_hash` is cleared and a still-`pending` `code_message` has `expires_at` set to now, in the same transaction, exactly as a resend's supersede does. Otherwise a code queued before mail went down is delivered when it returns, for a claim whose method is now `manual`. Submit's own flip has no code yet; the verify lock flip and `claim.start_verification`'s flip go through the shared helper. The message stays `pending` for the drain to expire. |
| **`mail_unavailable` folds into `ineligible`, ranked above the address** | `claim.verification_failed` keeps its four reasons; a fifth would be a spec change. On the submitted page the order is no website, locked pair, mail unavailable, address not at the host, because fixing the address cannot help once mail is down. The copy is recomputed on each view, so a claim submitted while mail was down and viewed after it was configured gets a neutral "reviewed manually" line, not a false address reason. |
| **Skip stores an empty `smtp` block** | `setup_state` counts the step done once the `smtp` key exists, and the sender reads an empty host as unconfigured, so `{"smtp": {}}` needs no other change. §4.3's pending-row rule governs anything queued meanwhile. |
| **The unconfigured-mail banner shows on every tenant admin page** | Shown to all staff while `available` is false. The link to the settings page is shown only to roles that can edit it. |
| **No provider presets** | SES hosts are per region and Gmail needs an app password, so a static host and port list is wrong on day one and rots. The port help text covers the three modes. |

## §4.7 — Worker tick jobs

New subsection. The #180 registry ruling and the jobs queued behind it (#132, #159, #193, #213), plus §11.2 payload nulling.

| Decision | Reasoning |
| -------- | --------- |
| **The tick registry is an instance, built by one composition root** (#180) | `audit.worker.jobs.build_tick_registry` is the only place that knows which jobs a worker runs; `run_worker.handle` calls it and hands the result to the loop. There is no module-level list and nothing registers at import time, so a second `handle()` in a process inherits nothing and no job outlives the `Command` whose stream it was bound to. A repeated name **raises** — silently ignoring it is what kept the first registration alive. |
| **Cadence belongs to the job's registration, not to the pass** | `run_due` runs every worker pass and each job declares `every`. `last_run` is stamped when a job is *attempted*, success or failure, so a job that raises waits out its cadence instead of being retried once a second. In-memory only: a restart runs every job once, which is safe because every job is idempotent. |
| **A tick job does bounded work and says whether there is more** | The tick shares a thread with the outbox and mail drains, so an unbounded job delays a claim-code email behind it. A job does at most one chunk per call and returns `TickResult(more=True)` while backlog remains; the job stays due and the worker does not idle. The CSV import already worked this way (`ROWS_PER_PASS`). |
| **`now` is required and keyword-only on every job** | One clock value per pass, threaded through. A test asserts it for every registered job; nothing in a job reads the clock. |
| **Tick failures are reported, not counted** | `worker_pass` writes each failed job to the worker's stderr. A retention job that has failed for a month is a compliance failure nobody was told about. |
| **The reindex drain resumes from a cursor** (#132) | `SearchReindexJob.cursor` is the highest listing id recomputed. A large marker is drained 200 listings a call across ticks and survives a restart. Only the marker being drained is stamped `done_at` — the command this replaced stamped every pending marker after a snapshot and lost any written in between. `rebuild_search_index` runs the same drain by hand; `--all` stays manual, since nothing writes a whole-tenant marker for a `search_config` change. |
| **Sitemaps are precomputed per tenant, change-detected by fingerprint** (#159) | Hooking every listing publish, unpublish and category write would couple the services to the worker. Each tick computes a cheap aggregate fingerprint per tenant (published count, `max(updated_at)`, id sum, listing-category pair sum, category and type routing fields, the absolute base) and renders **one tenant per call** only when it differs, at most once every five minutes per tenant — a bulk import must not cost a 50,000-URL render per row. Files go to the tenant's storage as a generation directory plus a `current.json` pointer written last. The views serve the stored file and fall back to live generation only for a tenant with no usable artifact (a cloud-storage tenant, #150, or before the first tick); the generated bytes are identical either way. An unverified domain has its artifact removed, per §4.1. |
| **Nulling a payload to `{}` with a stamp, not to `NULL`** | `OutboxEvent.data` is `NOT NULL` and the envelope always serialises a `data` object. `payload_nulled_at` separates "nulled" from "never had one". Nulled at 90 days from `created_at`, and only when nothing is left to deliver: the event is past fan-out and has no `pending` delivery. Dead letters are not exempt (§4, above). |
| **Payload nulling is the one permitted rewrite of a concluded command-log row** | Spec §11.2 says both "a concluded row is never rewritten" and "payload nulled at 90 days". The payload is a second copy of personal data, so the retention obligation wins, and it is the *only* exception: the `command_payload_retention` job sets `payload` to `NULL` and touches nothing else on the row — not the outcome, the problem, the timestamps or the result event id. A row whose command threw mid-apply (no `concluded_at`) is nulled on the same clock. The database does not enforce the rule (the app role holds `UPDATE`); a test asserts every other column survives. The spec wording is raised separately. |
| **`to_address` is nulled only on a terminal row** | A `pending` row is still going to be sent; the drain must never find its address gone. |
| **Retention sweeps run daily** | `import_pre_image_retention` (500 rows a call), `outbound_address_retention`, `event_payload_retention` and `command_payload_retention` (1,000 rows a call), each oldest-first. Window is strictly older than 90 days. |

## 5. Working conventions

- Branch, PR, squash-merge. Never commit to `main` — branch protection refuses it.
- `git commit -s` always. DCO is required by `CONTRIBUTING.md`.
- Conventional Commits. One concern per PR.
- `python manage.py check` and `python manage.py test` before opening a PR.
- `gh issue create` takes `--label`; labels are not applied otherwise, and a nonexistent label fails the whole command.
- Windows / PowerShell 7. Here-strings for file creation — `>` produces UTF-16 and breaks everything downstream.
- Migrations are forward-only. **A recorded migration is never edited.** A correction is a new forward migration, written to be idempotent so a from-zero database is unaffected. CI cannot catch an edited migration — it migrates from zero on every run, so an edited migration and a correct one are indistinguishable.
- `git checkout main; git pull` before every `git checkout -b`.
- Every entitlement state transition needs a test. That table is where this system rots if it rots.

### Prompting Claude Code

Prompts must be short — long ones fail to paste. Give it the task, the spec
section, and the constraint; let it read the rest.

**Ask "report, do not change" before accepting any layer that touches roles,
locks, or event emission.** Three real bugs in the Node build — a phantom
patch operation, a missing row lock, and a persistence layer that silently
required the database owner role — all surfaced from narrow read-only
questions, not from reviewing the diff. None would have been caught by a green
test run.

**When it flags a deviation from the spec, take it seriously.** It was right
six times in the Node build where the spec or the instruction was wrong, and it
correctly refuses to invent event names not present in the spec.

**Push back on generated bulk-rewrite scripts.** When it proposed a regex
rewrite of imports across 25 files, the right answer was to fix the compiler
setting so each site was identified individually.

**Numbers in a completion report are counted or omitted.** It reported "263
tests passing" and "30 new tests" in the same sentence with the same
confidence; the first was counted and correct, the second was estimated and
wrong by seven. Ask for the count command, not the number.

**A green suite cannot see cookie flags.** The Django test Client ignores
`Secure` and never sets `wsgi.url_scheme='https'`. Anything touching cookie
security is verified with a raw HTTP request against a non-loopback host, or
it is not verified.

**Unit tests that mock the database will not catch a missing table.** Run the
browser pass.

**A view gate is not a template gate.** `import_rollback` was manager-gated
while its template's `can_rollback` had no role term, so an editor saw a
button the view would 403. The role test varied batch state only. Green
suite; visible in five seconds in a browser.

**A test that reads an env var at import can pass in CI and fail locally on
the same commit.** #202. `OSDS_SECURE_COOKIES` must be `true` for the suite
and `false` for a plain-HTTP browser pass, and the two cannot share a
terminal.

Approve reads individually. Do not whitelist `git push`, `git add *`,
`docker exec *`, or anything that writes outside the repository.
