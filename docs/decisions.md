# OSDS — Decisions

Durable record of architectural decisions and current project state. Written
for a future contributor, or for pasting into a fresh AI session instead of
replaying prior conversations.

**Rule: decisions recorded here are settled.** Reopening one requires new
information, not a fresh opinion. If you disagree, open an issue arguing the
new information — do not relitigate in code or in a chat session.

Last updated: 2026-09-27

---

## 0. The reset

OSDS was first built in TypeScript — a pnpm monorepo of five packages on
Next.js, Kysely and Postgres RLS. That implementation is archived at tag
`v0-node`. It reached 444 passing tests, a working admin login, and a public
site, and it was several weeks from a shippable product.

**The build had diverged from the goal.** The goal is a system that is easy to
deploy and easy to manage, that hosts directory sites. The specification grew
to describe a mature product — premium slot concurrency, dunning windows,
agent escalation triggers — and the implementation chased the specification
rather than the goal. Correctness work on layers nobody could yet use is the
symptom.

The rebuild is Django 5 on Postgres 16, server-rendered, four containers.

**What carries forward:** every product, legal and behavioural decision below.
The specification's rules still bind.

**What is superseded:** everything about how those rules were implemented.
Kysely, the adapter-kit type union, `packages/*` boundaries, Postgres
row-level security as the tenancy mechanism, composite `(tenant_id, id)`
foreign keys, the `osds_app` non-owner role, scrypt session handling, the
`operator_login_attempts` design, and the five admin-surface routing rulings.
They were correct for that implementation. They are not decisions about this
one, and they are in git history if the reasoning is ever needed.

---

## 1. What OSDS is

A self-hostable, multi-tenant directory website system. An operator installs
it, defines one or more directories, populates listings, and sells upgraded
placements. Integrations with CRMs, payment providers, mail and SMS happen
through adapters. The system runs fully with none of them beyond the bundled
defaults.

Apache-2.0. Steward: Origin Development & IT, Inc. Repo: `OriginDevIT/osds`.

## 2. Product and legal posture

Unchanged by the reset. These are why the project exists in this shape.

| Decision                                         | Reasoning                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **No data-source connectors, ever**              | No importers, scrapers, hooks or plugin interfaces for external listing datasets. A system that ships an ingestion connector can be argued to have induced whatever the operator did with the data. A system that provides a database and a form cannot. Population paths are manual entry, CSV upload, owner submission and the write API. Spec §4.1.1. Contributions adding one are declined on sight. |
| **Link to external reviews, never display them** | A "Leave a review on Google" button is a hyperlink — always core, no adapter. Fetching and rendering a provider's ratings is governed by that provider's API terms. Optional adapter, operator's own credentials, operator accepts the terms.                                                                                                                                                            |
| **Consent is a required field**                  | On claim submission and lead capture. Records granted, timestamp, IP, plus a version pointer to an immutable copy of the exact wording shown. Evidentiary, for TCPA. Business phone numbers are not exempt.                                                                                                                                                                                              |
| **Apache-2.0, not AGPL**                         | Maximum adoption, clean for adapter authors, explicit patent grant. Accepted consequence: someone may host a competitor. Relicensing after outside contributions requires every contributor's consent, so this is effectively permanent.                                                                                                                                                                 |
| **Name is OSDS**                                 | Open Source Directory Site. Weak as a brand, precise as a description. Treat as closed.                                                                                                                                                                                                                                                                                                                  |

## 3. Functional decisions

The product rules. Framework-independent, and the reason the rebuild is a
rebuild rather than a restart.

### Tenancy and principals

| Decision                                                        | Reasoning                                                                                                                                                                                                                                                                                                                      |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Multi-tenant schema always; single-directory is a UI toggle** | Every tenant-scoped model carries a tenant reference from the first migration. Retrofitting tenancy is brutal; hiding a selector is trivial.                                                                                                                                                                                   |
| **All tenant data is tenant-specific**                          | No crossover between tenants, including users. A directory user belongs to exactly one tenant.                                                                                                                                                                                                                                 |
| **Two kinds of person**                                         | A **user** owns or seeks to own a listing and belongs to one tenant. An **operator** administers directories, belongs to no tenant, and is one login across the installation. Both have an email address, which is not a reason to merge them. Spec §4.3, §4.4.                                                                |
| **Staff membership is the link**                                | `StaffMembership(operator, tenant, role, status)`. No row means no access to that tenant, whatever the operator holds elsewhere. Admins may therefore be tenant-specific or multi-tenant, with no separate concept for either.                                                                                                 |
| **Two axes, not one ladder**                                    | `is_superadmin` on the operator; `role` on the membership. Creating or suspending a tenant happens outside any tenant, so no membership can authorise it. Everything else is per-tenant.                                                                                                                                       |
| **Superadmin holds no implicit tenant access**                  | They add themselves a membership at a stated role. Unpreventable in principle — anyone who can assign memberships can assign their own. The point is evidence: a grant leaves a row and an event, so hosting-side access to a client's directory is a fact on the record rather than an invisible capability.                  |
| **Five ordered role ranks**                                     | `admin` 4, `manager` 3, `editor` 2, `moderator` 1, `support` 0. Authorization is `rank >= n`. The load-bearing cuts are 3/2 (money and PII) and 2/1 (authority over other people's listings). A capability matrix is the right shape only when roles are configurable, and these are not.                                      |
| **Memberships on an existing operator start pending**           | Otherwise an admin of one tenant can silently attach a directory to the account of an admin of another. A membership minted together with its operator activates on password set — accepting the invitation and the membership are one act.                                                                                    |
| **Invitation never writes to an existing operator row**         | Membership only, and the response is identical whether the email matched. Match-and-update on an invite form is cross-tenant account takeover. A differing response is an oracle for which clients administer other directories on the installation.                                                                           |
| **Tenant admin lives at `/admin` on the tenant's own domain**   | The DNS record and certificate already exist for the public site. A second hostname per tenant is another record the operator must get right before they can log in at all, and a lockout with a DNS error is the worst first experience available.                                                                            |
| **The console is a separate host and is not a tenant**          | Installation-level operations and a directory picker. Every operator reaches it, because accepting a pending invitation happens there. Clicking a tenant opens that tenant's `/admin` and does not carry the session — a cross-host handoff token is a new credential type and the piece most likely to be built subtly wrong. |

### Listings

| Decision                                                                  | Reasoning                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Directories have a type**                                               | Businesses, locations, people, services, software and others. A listing type carries a field schema; type-specific columns would be a rewrite per type. Spec §4.5.                                                                                                                                                                            |
| **Tiers are tenant-configured**                                           | An ordered list with a `rank`. Rank 0 is the fallback tier. Core hardcodes no tier names. A tenant may define no rank-0 tier, which changes downgrade behaviour.                                                                                                                                                                              |
| **Provenance is recorded on every listing**                               | Source, import batch, submitter. Four operational reasons: dedupe across population routes, undo of an import batch, removal that sticks via a suppression key, and trust display on the public page. Not about upstream licensing.                                                                                                           |
| **Removal sticks**                                                        | A deleted listing records a suppression key — normalised name, address and phone hash — that subsequent imports check against, so a removed business does not reappear on the next CSV upload.                                                                                                                                                |
| **Rollback restores updated rows, not just created ones**                 | A batch both creates and updates. Removing only the creations leaves every updated row carrying imported values with no way back. Rollback deletes created rows and re-applies a pre-image to updated ones. Rejected: refusing rollback on any batch that updated a row — most re-imports update, so that refuses the common case. Spec §3.3. |
| **A pre-image is nulled at 90 days, and a nulled batch cannot roll back** | The pre-image is a second copy of personal data — the thing §11.2's nulling rule exists to prevent, and the same reasoning that denies dead letters an exemption. The admin UI states the batch is past its rollback window rather than offering a button that half-works.                                                                    |
| **Rollback writes no suppression key**                                    | The key exists so a business the operator removed does not reappear on the next upload (§4.1.1). A listing removed because the operator undid their own import is not that case, and suppressing it makes the undo permanent. Rollback emits `import.rolled_back` only — no per-listing `listing.deleted`.                                    |
| **Search is core**                                                        | Postgres full-text plus trigram matching, working on a fresh install with no configuration and no extra container. External engines are an optional upgrade. A default deployment must never produce a directory nobody can search.                                                                                                           |
| **Sitemap index from day one**                                            | URL count grows faster than listing count — categories × locations × pagination crosses 50,000 URLs on a 5,000-listing directory. Decide deliberately which facet combinations are indexable.                                                                                                                                                 |
| **`visibility` is a rejected field on `listing.upsert`**                  | It joins `tier` and `status`. Publishing emits `listing.published`, so an upsert that could flip it would either emit an event its outcome table does not name, or bury a publication change inside a JSON Patch. A CSV re-import must never publish a draft as a side effect of touching a phone number. Spec §7.1.                          |
| **`draft ↔ hidden` emits nothing**                                        | Neither state is publicly visible, so nothing became visible or hidden. Only crossing the `published` boundary emits.                                                                                                                                                                                                                         |
| **A listing never changes its type**                                      | An id-matched upsert naming a different `listing_type` is a 422. The type determines the field schema; changing it orphans every custom value.                                                                                                                                                                                                |
| **Removing a field from a type orphans its values**                       | No sweep, no block. The values stay in `custom_fields`, invisible, and re-adding the key restores them. A destructive data migration triggered by an admin unchecking a box is worse than dead JSON keys.                                                                                                                                     |
| **A type's `key` is frozen after creation; `path_segment` is not**        | `key` appears in patch pointers and event payloads that adapters route on. `path_segment` is editable and writes a `PathRedirect`, because the operator will get the URL wrong the first time and the alternative is recreating the type.                                                                                                     |
| **Category paths are one level in the URL**                               | Regardless of tree depth. `/plumbers/hoffman-plumbing` even where `plumbers` sits under `trades` for browsing. Deep nesting multiplies indexable paths for no gain, and slug uniqueness is already per `(tenant, listing_type)`.                                                                                                              |

### Claims

| Decision                                                      | Reasoning                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Manual admin review is the default and always available**   | Records the method used, who verified, when, and mandatory notes — an admin who cannot articulate how they verified has not verified.                                                                                                                                                                                                                                                |
| **Email OTP ships alongside manual at launch**                | Phone OTP, postcard and Google Business Profile OAuth are planned and must not be designed out. Phone OTP is the eventual workhorse. GBP requires a separate approved Google Cloud project per self-hoster, so it is optional and never default.                                                                                                                                     |
| **Core computes code expiry, never the caller**               | A lifetime is a rule. Tenant-configurable within bounds core enforces; a value outside the bounds is rejected at configuration time, not silently clamped at use.                                                                                                                                                                                                                    |
| **Notify every existing contact channel on successful claim** | Catches what verification misses, costs almost nothing.                                                                                                                                                                                                                                                                                                                              |
| **Mask contact details in the verification UI**               | Otherwise the claim flow is a phone-number disclosure endpoint for every listing on the site.                                                                                                                                                                                                                                                                                        |
| **Disputes go to moderation, never auto-transfer**            | A second claim on a claimed listing opens a moderation item. Verification alone never moves ownership away from a sitting owner.                                                                                                                                                                                                                                                     |
| **The verification code is hashed, never stored or emitted**  | `claim.verification_started` carries `method`, `expires_at` and a masked destination only. The bundled `webhook` adapter is default-enabled, so a code in the payload is a live credential POSTed to an operator-supplied URL and retained for 90 days by §11.2. Core compares a hash; the plaintext exists only in the message sent. Spec §9.6.                                     |
| **`domain_email` matches the listing's website host**         | Leading `www.` stripped, nothing else. A subdomain website requires a subdomain email. No website, no match, or a platform page → manual review with the operator notified. A claimant who cannot receive mail at the business's own domain has not demonstrated what the method claims. Rejected: matching `contact.email`, which only requires reading the public page. Spec §9.6. |
| **Attempt limits are core's, not tenant-configurable**        | Five wrong codes kill the code and open a 15-minute cooldown on `(listing, email)`; three cooldowns lock the pair to manual with a moderation item. An operator raising a brute-force ceiling on a form field is not making a security decision knowingly — the reasoning §9.5 already applies to lifetimes. Spec §9.6.                                                              |
| **Three rejections block that email on that listing**         | A rejected claimant may resubmit; §9.3's mandatory notes are what tell them what was missing. Three blocks the pair, opens a moderation item, and only an operator unblocks. Scope is the listing, never the tenant — someone rejected on one business may own another, and a tenant-wide email block is a support call. The rejection and cooldown counters never reset each other. |
| **An owner signs in with an emailed link, never a password**  | 12-hour link, session expiring after 12 hours idle. No credential on a user row, so no reset flow and no lockout policy. §4.3 warns that reusing a user row on an email match stops being safe once a stored credential outlives the verification that justified it; a link re-proves mailbox control on every entry, which closes that without a second credential store.           |

### Entitlements and money

| Decision                                      | Reasoning                                                                                                                                                                                                                     |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Core owns entitlement; adapters own money** | Payment adapters report outcomes. Core decides tier consequences. **There is no command that sets a listing's tier** — with a settable tier, any adapter becomes the source of truth.                                         |
| **Payments ship at launch**                   | Comps and paid entitlements both. The full lifecycle seam — status, period end, payment reference — is built once rather than retrofitted.                                                                                    |
| Dunning window                                | 14 days. Most failed payments are involuntary — expired cards, not churn.                                                                                                                                                     |
| Public display during dunning                 | Full perks retained. Demoting someone whose card expired is invisible to them and loses customers who intended to pay.                                                                                                        |
| Grace after dunning                           | 30 days, downgraded, restore path open.                                                                                                                                                                                       |
| At expiry                                     | Downgrade to rank 0, **never unpublish**. Unpublishing destroys an indexed page and reads as punitive. Exception: a tenant with no rank-0 tier hides the listing, and the admin UI must say so at the point of configuration. |
| Cancellation                                  | At period end, skips grace. They chose to leave; grace exists for involuntary failure.                                                                                                                                        |
| Refund                                        | Immediate downgrade.                                                                                                                                                                                                          |
| Data collected while paid                     | Retained, access gated. Never delete leads or reviews on downgrade. "You received 34 leads while on Featured" is the best renewal prompt available.                                                                           |
| Trials                                        | Card required up front. Off by default on slot-backed tiers.                                                                                                                                                                  |
| Comps                                         | Consume sellable slot capacity. Anything else makes capacity numbers lie.                                                                                                                                                     |
| Proration                                     | The payment adapter computes it; core receives a new period end. Keeps fiddly arithmetic in the system that already solves it.                                                                                                |

### Slots — first post-launch addition

Not built for launch. Rotation of unsold placements and locked capacity are
separable and may land earlier.

| Decision         | Reasoning                                                                                                                                                                                          |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Waitlist notice  | T-10 days, worded "_may_ become available". The incumbent holds right of first refusal until the moment of expiry. Overstating availability generates complaints.                                  |
| Unsold slot fill | Locked → default featured → random rotation. Rotation means a new directory never shows empty slots, and free listings get intermittent premium placement — the best upgrade pitch available.      |
| Allocation       | One row per capacity unit, locked with `FOR UPDATE SKIP LOCKED`. The row _is_ the lock. Over-sell is impossible by construction. Rejected: counter columns, advisory locks, materialize-on-demand. |

### Adapters

| Decision                                                       | Reasoning                                                                                                                                                                                                                                                        |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Core never imports adapter code**                            | No vendor name appears in core. Core knows capability names only. This is what keeps any single vendor from becoming a dependency of the project.                                                                                                                |
| **Adapters never write core listings directly**                | They send commands; core validates, applies and emits. An adapter that writes the database bypasses event emission and the command log.                                                                                                                          |
| **Postgres outbox, no message broker**                         | Events written in the same transaction as the state change, drained by a worker. Zero extra containers keeps one-click self-hosting viable. A directory does not generate broker-scale traffic.                                                                  |
| **Delivery is at-least-once**                                  | Adapters dedupe on event id. Ordering is guaranteed per subject, never globally.                                                                                                                                                                                 |
| **Loop prevention is structural**                              | Core stamps the originating adapter id on the resulting event; an adapter ignores any event it originated.                                                                                                                                                       |
| **PII is opt-in per adapter**                                  | Redaction is the default.                                                                                                                                                                                                                                        |
| **Agent restrictions are scopes, not prompts**                 | No entitlement commands, no compliance commands, no deletion, mandatory transcript reference, global kill switch. A restriction that exists only in prompt text is not implemented. Agents are post-launch; the scope model must not be designed out.            |
| **Three logs, three retentions**                               | Event log (envelope forever, payload nulled at 90 days), command log (forever, including rejected and blocked), access log (2 years, separate store). The payload is a second copy of personal data — the copy people forget when processing a deletion request. |
| **The command log is written outside the command transaction** | Recorded before the transaction opens, concluded after it settles. A log written inside the transaction it is logging disappears when that transaction rolls back — which is exactly the case the log exists for. A concluded row is never rewritten.            |

### Deployment

| Decision                                  | Reasoning                                                                                                                                                                                         |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **First-run wizard, never config files**  | The target operator can rent a server but should never edit YAML to set an admin password. The wizard sets the superadmin, the first tenant, its domain, storage, SMTP and enabled claim methods. |
| **The wizard assists with DNS**           | It shows the record to create and verifies it, rather than assuming the operator knows. A lockout behind a DNS error is the worst first experience available.                                     |
| **Setup token printed to container logs** | Plus the route disappearing once an operator exists. The gap between bringing the stack up and opening a browser is a real window on a public IP, and the count check alone does not cover it.    |
| **Four containers**                       | App, worker, Postgres, object storage — the last two replaceable by managed services through configuration alone. A fifth container to support any single feature is a decision, not a detail.    |

## 4. Implementation decisions — Django

New. These are decisions about the current implementation only.

| Decision                                                                         | Reasoning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Django 5, Postgres 16, templates plus HTMX**                                   | Server-rendered fits a directory. No SPA framework, no build step for the public site.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Row-level tenancy via a scoped default manager**, not RLS or schema-per-tenant | Schema-per-tenant makes the cross-tenant console query N queries. Postgres RLS remains the correct defence in depth and is planned, but app-level scoping ships first. **The consequence is accepted and named: one unscoped query is a cross-tenant leak.** A test asserts every tenant-scoped model's default manager is the scoped one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Writes go through a service layer**                                            | The ORM does not emit events or write the command log. Django admin is disabled for tenant data for the same reason — it writes tables directly. Django admin is used for the installation console only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **The console admin writes through services, never `save_model`** (#146)         | Registering `Tenant`, `Operator` and `StaffMembership` in the console admin is consistent with "Django admin is disabled for tenant data" — these are principal and structural models, not tenant data. But a raw admin save emits nothing, so each goes through its service function: `Tenant` emits `tenant.created`, `StaffMembership` emits `staff.invited`. **`Operator` creation emits no event and writes the command log only.** An operator belongs to no tenant, and §4.4 already reasons that installation-scoped acts fit neither envelope arm — `OsdsAnyEvent` is `OsdsEvent \| TenantEvent`, and a tenant block would be a lie. `command_log` takes a null `tenant_id` for exactly this case (§11.2), which is the audit trail that matters. An `operator.*` namespace would mean widening the envelope union and is a spec change, not an implementation decision. **This surface emits `staff.invited` only** — `staff.accepted` fires when a pending membership is accepted, and there is no set-password acceptance view (#163). |
| **The console admin bypasses the changeform entirely, not just `save_model`**    | `ModelAdmin.changeform_view` wraps `_changeform_view` in `transaction.atomic`, so routing a write through the built-in add form — even with a custom `ModelForm` — puts the command log inside the transaction it exists to survive (§11.2). `add_view` is overridden outright and never calls `super()`, which means re-supplying the `csrf_protect` decorator and the explicit `has_add_permission` check the bypassed view normally provides. Forms are plain `forms.Form`, never `ModelForm`: a `ModelForm` carries an `instance` and a `.save()`. `save_model` and `save_related` raise `NotImplementedError` so a later permission change cannot silently reintroduce an ORM write. The acting operator is `request.user`, passed to the service as an explicit kwarg — never a ContextVar, since no tenant is resolved on the console host.                                                                                                                                                                                                 |
| **No Celery, no Redis, no broker**                                               | Celery has no supported Postgres broker; the SQLAlchemy and Django transports were dropped. Adding it means a fifth container and breaks one-click self-hosting. Scheduled work — dunning transitions, grace expiry, term expiry, renewal notices, payload nulling, sitemap regeneration — runs in the worker's tick loop. If a real queue abstraction is later needed it must use the database as its broker.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Long work is queued, never in-request**                                        | CSV import, media processing and mail run on the worker. A several-hundred-row import times out a browser request. The upload stores the file and creates a batch row; the worker processes it. **One accepted exception: import rollback runs in-request (#192)** — it is one transaction over the rows of a single batch, not an unbounded loop, and queueing it would mean a second status surface for an operation the operator is watching. Named here because an unrecorded exception is how the rule erodes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Mail leaves through an `OutboundMessage` row, not the outbox**                 | Core writes the message in the same transaction as the state change that caused it; the worker drains it and calls whatever is registered under the capability name `email.send`. Core imports no vendor code — `osds/adapters.py` is the seam it already was. The outbox is the wrong carrier: a verification code in an event payload is a credential handed to the default-enabled `webhook` adapter and kept 90 days. A minimal bundled `smtp` sender on stdlib `smtplib` against the wizard's SMTP settings is **pulled forward from block 5** so email OTP can ship in block 3; the block-5 adapter replaces the sender without core changing. No new dependency, no fifth container.                                                                                                                                                                                                                                                                                                                                                        |
| **No `post_save` audit package**                                                 | `django-auditlog` and `django-simple-history` record what succeeded, inside the transaction that succeeded. The command log's purpose is rejected and blocked attempts, written outside the command transaction. A signal-based package structurally cannot see the rows that matter most. Both logs are hand-rolled.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Storage is per-tenant, resolved at runtime**                                   | `django-storages` reads settings at import time, and wizard-entered credentials live in the database. A thin backend resolves the target from tenant configuration per request. Local disk is the default; S3, Azure and GCP are configurable in the wizard.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Geo is `lat`/`lon` plus raw-SQL distance**                                     | GeoDjango needs GDAL and GEOS binaries the development machine does not have. Radius search works without them. PostGIS is planned server-side.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **A devcontainer is planned, not deferred indefinitely**                         | Anything that genuinely requires Linux-only native binaries pulls it forward immediately.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Event names live in a constants module**                                       | With a test asserting every emitted type appears in it. This replaces the TypeScript union that made a typo a compile error.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Settings raise at import for required secrets**                                | `DJANGO_SECRET_KEY`, `OSDS_SECRET_KEY` and `DATABASE_URL` have no defaults. A default encryption key in a public repository means an operator who forgets the variable encrypts their storage and mail credentials with a value anyone can read. `DEBUG` defaults to False.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **`ALLOWED_HOSTS` is `['*']`; the middleware is the host gate**                  | Tenant domains are added at runtime and cannot be enumerated statically. `TenantResolutionMiddleware` runs **before** `SecurityMiddleware` — with `ALLOWED_HOSTS` permissive, nothing validates the Host header until it does, and an SSL redirect built from an unvalidated host is a redirect-poisoning primitive.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **`ATOMIC_REQUESTS` stays False**                                                | `upsert_listing` raises when a caller already has a transaction open, because the command log must commit independently of the command it logs (§11.2). Request-wrapped transactions would break every write path. Pinned explicitly rather than relying on the default.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Migrations run as the database owner**                                         | `CREATE EXTENSION pg_trgm` and `CREATE INDEX` need the owner role. The container entrypoint migrates with `DATABASE_URL_ADMIN`; the app runs on the least-privilege `DATABASE_URL`. Deploy wiring, not a settings branch.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **No object-storage container at launch; media is a named volume** (#178, #150) | §3 names four containers, the last being object storage. Storage is local disk only (#150): `get_tenant_storage` has no S3 path, and adding one needs `boto3`, a human-gated dependency. A MinIO container would run with nothing attached while the wizard's S3 option still raised the deferred-feature error. At launch the fourth container is therefore the `osds-media` named volume, mounted at `OSDS_MEDIA_ROOT` in **both** `osds-app` and `osds-worker` — the worker reads uploaded CSVs from it. When the S3 backend ships, the compose file gains a `minio` service in the same PR. Spec §13 still lists `minio`; that is a spec edit and is raised separately. |
| **Secrets are generated at first boot into a named volume, not a config file** (#178) | The target operator never edits a config file (§3). On first boot the `postgres` container — the first up, and the only one needing a secret before anything else — writes `db_owner_password`, `db_app_password`, `django_secret_key` and `osds_secret_key` into the `osds-secrets` volume, once, as hex. Postgres reads its password through `POSTGRES_PASSWORD_FILE`; the app entrypoint exports the others **only for a variable not already set**, so a `.env` override wins and a truly unset variable still makes `settings.py` raise. `.env` is optional overrides only. No one-shot fifth container. The owner URL exists only in the entrypoint's shell and is unset before gunicorn or the worker starts. **The consequence is accepted and named: losing `osds-secrets` loses `osds_secret_key`, which encrypts every credential stored through the wizard, and nothing else can decrypt them.** The README says so. |
| **A migration that imports live code names a frozen function**                   | 0004's backfill calls `recompute_search_vector_v1`, documented as frozen migration history. CI migrates from zero, so the loop body never runs and behaviour drift is undetectable. The naming convention makes such an edit an obvious violation rather than an innocent refactor.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Vendored front-end assets, never a CDN**                                       | htmx is committed with a provenance header. The admin runs on an authenticated tenant session; a CDN load is a third-party script on that session and leaks the tenant's domain on every page.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Authentication writes to no log**                                              | Spec §11.2 defines three logs: events, commands, access. A session is none of them — no command verb, no outbox event, no view or export of data. `last_login` is the only record kept. The Node-era `operator_login_attempts` table is superseded (§0) and is not reintroduced under another name. Login auditing means a new `AccessLog` action argued in an issue, not a fourth log.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **`SECURE_PROXY_SSL_HEADER` is set; `CSRF_TRUSTED_ORIGINS` is not**              | Tenant domains are runtime rows and cannot be enumerated in settings — the same constraint that produced `ALLOWED_HOSTS = ['*']`. Login POSTs are same-origin, so Django's host comparison suffices, but only if Django knows the request scheme. Behind TLS termination it does not, the origin check compares `https` against `http`, and every login POST is a 403. Safe only because the deployment proxy is required to strip a client-supplied `X-Forwarded-Proto`. **Superseded in part by §4.13:** the header is believed only from a peer in `OSDS_TRUSTED_PROXIES`, and its rightmost token is used, so the proxy is no longer relied on to strip it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **The first-run wizard relaxes cookie `Secure`**                                 | Served over plain http before any TLS, the wizard's `Secure` session and CSRF cookies are dropped by the browser, so first boot cannot pass CSRF or hold its unlock flag. `SetupCookieSecurityMiddleware` strips `Secure` from those two on `/setup/` responses while `InstallSetup.completed_at` is null. The gate is that route plus setup being incomplete, with no `request.is_secure()` check, and self-destructs when completion stops the setup URLconf resolving.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Per-adapter delivery state is its own table** (#171)                           | `OutboxDelivery`, one row per `(event, adapter_id)`. §8.2 gives each adapter an independent attempt count and backoff, and one status column on `OutboxEvent` holds one consumer's progress. `OutboxEvent.status` therefore means **fanned out**, not delivered. The `tenant` FK is nullable because `tenant.*` events carry no tenant block — and **a nullable tenant is not the §11.2 `command_log` exception**: that exception is bounded and argued, and taking it by analogy is how the tenancy invariant rots. `OutboxDelivery` carries the tenant-scoped default manager and `all_tenants` like any other tenant-scoped model. `subject` is denormalised onto the row so the head-of-line ordering check never joins `outbox_events` on the claim path.                                                                                                                                                                                                                                                                                     |
| **The drain holds no row lock across the handler**                               | A short transaction takes `FOR UPDATE SKIP LOCKED`, pushes `next_attempt_at` to a 90-second visibility deadline and commits; the handler runs unlocked; the result lands in a second short transaction. A 30-second handler (§8.2) inside `FOR UPDATE` would pin a connection and a transaction for its whole attempt. A crashed worker's delivery becomes claimable again when the deadline passes. **`_record` is therefore a conditional update keyed on the deadline the claim stamped:** a handler that hangs past 90 seconds has its row re-claimed and finished by a later pass, and its eventual write must not land. At-least-once covers a duplicate delivery; it does not cover a double-incremented `attempt` or a stale `retried` overwriting a `delivered`. `attempt` increments only after the handler returns, and `BaseException` propagates untouched — a `KeyboardInterrupt` mid-handler is a shutdown, not a failed attempt.                                                                                                   |
| **Dead letters are not exempt from payload nulling**                             | A dead `OutboxDelivery` is replayable from the admin (§8.2), but its event's `data` is nulled at 90 days like every other payload (§11.2). Exempting dead letters rebuilds the shadow copy of personal data that the nulling rule exists to prevent, and a 90-day-old dead letter is not worth replaying. Replay older than that reconstructs from current state.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Operator settings saves are in the command log** (#225) | Every successful save from a tenant-admin or first-run-wizard settings page writes one `settings.update` row: mail, adapter settings, payment settings, lead form, tiers, listing types and their field schema, categories, and the wizard's domain, storage, mail-skip and claims steps. Actor is the operator's public id; the payload is `{page, op, fields}`, the page name, `add`/`replace`/`remove`, and the **names** of the fields that changed, never a value. A secret is named like any other field and its value is never read. A save that changes nothing still writes a row, with `fields` empty. A refusal the service raises (`InvalidTenantSettings`, `AdapterSettingsError`, `TierError`, `SchemaError`, the delete-in-use `ValueError`) concludes the row `rejected` with the fixed `problem` `{"reason": "invalid"}`, never the message, which can quote a submitted value. A form that fails validation never reaches the service, attempts no command, and writes nothing. The row follows §11.2 like every other command: received before the save's transaction opens and concluded after it settles, each committed on its own, so the service functions run in autocommit and refuse a caller's transaction (`MustNotBeInTransaction`). The ruling as first stated asked for the row inside the save's transaction; that would lose a rejected row on rollback, which is the case §11.2 says the log exists for, so it is not what ships. `audit.command_log.settings_command` is the one helper; each page's public service wraps an atomic `_apply_*`. Rotating an adapter secret stays `adapter.rotate_secret`. The console admin's `Tenant`, `Operator` and `StaffMembership` writes are principal models with their own commands and are out of scope. |

## §4.3 — Outbound mail

New subsection. Claims PR 2 rulings.

| Decision | Reasoning |
| --- | --- |
| **`OutboundMessage` is one table with delivery state on the row** | One consumer and no fan-out, so a per-consumer table like `OutboxDelivery` would always hold exactly one row. The drain mechanics are copied exactly: a `SKIP LOCKED` claim, a 90-second visibility deadline, and a result recorded only if the stamped deadline still matches. The concurrency hazards do not depend on consumer count. Statuses `pending \| sent \| dead \| expired`; §8.2 backoff. |
| **`expires_at` is required and bounds every message** | The producer sets it to the code's or link's own expiry; a notice with no natural deadline gets one from its producer. Past it, the drain marks the row `expired` and never sends. A code delivered after it died reads as live and burns §9.6 attempts. `expired` tells the operator SMTP was down long enough to kill a message, which `dead` does not. Originally nullable: with no attempt ceiling, a null deadline let a retryable error such as a wrong SMTP password retry forever without ever nulling the body. Rejected: §8.2's 12-attempt ceiling, which dead-letters a security notice after about 68 minutes of misconfiguration. `dead` is reserved for recipient refusal. |
| **`body_text` is nulled on terminal state; `to_address` at 90 days** | The body holds the plaintext code, and §9.6 says the plaintext exists only in the message sent. It is nulled in the same write that sets `sent`, `dead` or `expired`. The address is kept for delivery debugging and nulled at 90 days per §11.2 by the daily `outbound_address_retention` tick job (#213, §4.7), and only on a terminal row. `subject` is template text and stays. |
| **`OutboundMessage.tenant` is non-null** | It fails the §11.2 `command_log` exception on two of its three conditions: it is a pending state change the drain reads back and updates. Operator invitation mail is installation-scoped and is #163's design problem. |
| **Capabilities resolve through `capability_provider(name)` in `osds/adapters.py`** | Beside the event subscribers. One provider per capability; a second registration raises. The `smtp` sender lives in `adapters/smtp/` and is wired by the `osds` bootstrap (§8.6). A test asserts nothing under `directory/`, `tenants/`, `billing/` or `audit/` imports `adapters`. Rejected: a separate `osds/capabilities.py`, because two registry modules drift. |
| **Unavailable mail leaves the row pending** | With no provider registered, or empty SMTP settings or `from_email`, no attempt is consumed and no backoff applies. The row is rechecked on a fixed 60-second interval, and `expires_at` governs. A pass whose only mail activity was unconfigured rows is not work and idles: counting it made the worker busy-loop with no wait, caught in the browser pass. The drain logs one aggregate line per pass at WARNING, because the project ships no `LOGGING` configuration and an INFO record is discarded; a real configuration belongs with #179. Treating unavailable mail as a failure would dead-letter every message queued before the operator configured mail. This is the state #121's skip action produces. |
| **#121 follows PR 2 as its own PR** | Wizard UI and a credentials surface, both human-gated. The drain needs nothing from it once unconfigured mail is a defined state. |
| **The mail drain runs every worker pass, not as a tick job** | Beside the outbox drain, on the 1-second idle poll, with no NOTIFY. A user-facing code does not belong on a tick period, and a drain does not need the tick registry. |
| **`enqueue` raises outside an atomic block** | The mail ruling's guarantee is atomicity with the causing state change: a stored hash with no message, or a message with no hash, is a broken claim. The inverse of `upsert_listing`'s guard, enforced for the same reason. |
| **Sending emits no event and writes no command log** | §3.3 has no mail namespace and PR 2 does not invent one. The causing command already emits and logs. Delivery state is on the row. An adapter needing delivery events is a spec addition argued in an issue. |
| **The bundled sender is stdlib only** | `smtplib` and `email.message.EmailMessage`, plain text. Settings are read per send from the database, with credentials via `Secret`. 30-second timeout (§8.2). TLS per `smtp.security` (§4.5), never downgraded. Logs `message_id` and the error class only: §8.3 forbids logging contact values, and #179's redaction does not exist yet. A recipient 5xx is permanent and goes to `dead`; connection errors and 4xx retry. Rejected: `django.core.mail`, which contradicts the settled stdlib wording. |
| **Local mail is tested against Mailpit, a dev-only container** | Python 3.12 removed `smtpd`, and `aiosmtpd` would be a new dependency. Mailpit is never in `requirements.txt`, the compose file or the runtime. |

## §4.4 — Claim verification

New subsection. Claims PR 3 rulings, `domain_email` only.

| Decision | Reasoning |
| --- | --- |
| **A correct code records success and stops** | It sets `Claim.verified_at`, clears `code_hash` and concludes `claim.verify` as `applied`. Status stays `pending_verification`, and no success event is emitted. PR 4 moves approval into the same transaction: `claim.approved` on an unowned listing, dispute on an owned one, and any claim already carrying `verified_at` is consumed. Rejected: emitting `claim.approved` without the owner write and the notice, which breaks #48 and §9.4. Rejected: absorbing approval into PR 3, which makes it two concerns. The window between the merges exists only on dev databases. Nothing in PR 3 moves ownership, including away from a sitting owner. |
| **Verification starts inside `claim.submit`; resend and restart go through `claim.start_verification`** | Both call one internal start function. It generates the code, stores the hash, sets `expires_at`, calls `enqueue` and emits `claim.verification_started`, in the caller's transaction. The common case needs no second click. The restart that §9.6's cooldown forces reuses the same generator and hash path. |
| **The verified address is the claimant's submitted email** | It is the address `DirectoryUser` is matched on, and where the owner's sign-in link will go. Verifying a different address would leave the user row with an address nobody proved, which is the case §4.3 warns makes row reuse unsafe. |
| **An ineligible `domain_email` claim flips to `manual` in the service** | Ineligible means no website, a platform website, or an address not at the website's host. This follows §9.6 as written. §4.5 adds a fourth reason, mail unavailable. `claim.submitted` carries `method: manual`, no code is produced, and the requested method survives in the command-log payload. `claim.start_verification` re-checks and flips too, because an import can change the website. `ClaimForm` offers `domain_email` only for an eligible listing and shows the required `@domain`, which the masked destination already discloses. Rejected: a form error, which contradicts §9.6. |
| **Platform hosts are a fixed core list** | These are social, marketplace and free-hosted-site registrable domains, matched on equality or subdomain. They are not tenant-configurable, for §9.6's reasoning on limits. Both hosts are normalized before comparison: lowercase, IDNA to ASCII, port and trailing dot stripped, and exactly one leading `www.` stripped from the website host only. A test pins a sample of the list. |
| **Operator notification ships with the review queue** | §9.6's "operator notified" ships in PR 4 with the manual-review surface, so the notice links to something actionable. It covers every claim entering manual review, flipped or chosen. #218. |
| **The code is six digits under a keyed hash** | `secrets.randbelow(10**6)`, zero-padded. Five entries per window and three windows make 15 guesses per pair, about 1 in 67,000. `code_hash` is Django `salted_hmac` with salt `osds.claim.verification_code` over `f"{claim.public_id}:{code}"`, sha256, compared with `hmac.compare_digest`. A plain digest of a six-digit code reverses from a dump in under a second. Rejected: PBKDF2, whose slowness buys nothing once the key defeats offline attack. Rejected: keying from `OSDS_SECRET_KEY`, which guards stored credentials and is heavy to rotate. |
| **TTL is read from §9.5's configuration shape** | `settings["claim_verification"]["ttl"]["domain_email_minutes"]`, 1440 when absent. The code's `expires_at` is the `expires_at` passed to `enqueue`. |
| **§9.5 bounds are a core constant validated at configuration** | Bounds for all three code methods live in one constant. They are validated by `update_tenant_settings` for the `claim_verification` key, and an out-of-bounds or wrongly typed value is rejected. `ClaimsForm` reads its limits from the constant. At use, a stored value outside the bounds, which only direct SQL can produce, falls back to the method default with a WARNING. That is a default, not a clamp. #209. |
| **Code entry is bound only by the claim ID** | `/claim/<claim public_id>/verify/`. The code is the authenticator, and attempts are counted per pair, not per browser. A session binding strands a claimant who switches device and stops no one, because the attacker who can lock a pair filed the claim and holds every URL. The email carries the code and a plain link to that page. The code is never in a URL, because mail scanners follow links. |
| **`claim.verify` logs the claim ID only** | The payload is `{"claim_id"}`, never the entered code or its hash. The actor is the claimant's user `public_id`, never an email (#219). A wrong code concludes `applied` with `result_event_id` set to its `claim.verification_failed` event, because it changes state. `rejected` is reserved for guard refusals that change nothing. `claim.start_verification` uses the same payload and actor shape. |
| **No claimant or lead PII in the command log** | The log is permanent and its rows are written outside the command transaction, so a submitted email, name, phone or message would outlive the record it came from. `claim.submit` is anonymous and has no user row until it applies, so its actor is `{"type": "visitor", "id": "claimant:<claim public id>"}`, the claim id minted before the transaction opens and used for the claim if it is created. On a refused or blocked attempt it names no claim, and serves only to correlate that attempt's rows. An unknown `method` or lead `kind` is reported as "is not one of" the allowed values, never echoed. Its payload is `listing_id`, `method`, `claim_id` and `consent`, with no `claimant`. `lead.create` keeps its empty visitor actor and logs `listing_id`, `kind` and `consent`, with no contact, message or `source_page`. A malformed phone number is reported without the value. The email, name and phone stay on the claim, the user, the lead and their events. No migration or backfill: no installs exist. #219. |
| **The counters live on a per-`(listing, claimant)` guard row** | The row is keyed on the `DirectoryUser` FK, so no second copy of the address is stored. Fields: `wrong_entries`, `cooldowns`, `cooldown_until`, `verification_locked_at`, `rejections`, `claim_blocked_at`, `last_code_sent_at`, `codes_sent_window_start`, `codes_sent_in_window`. It is taken `select_for_update` on every entry. A count on the code would be reset by a resend, a route around the limit exactly like a rejection resetting it. The fifth wrong entry clears `code_hash`, opens a 15-minute cooldown, increments `cooldowns` and zeroes `wrong_entries`. The third cooldown sets `verification_locked_at` and flips the claim to `manual`. `submit` refuses a pair with `claim_blocked_at` set; nothing writes `rejections` until PR 4. `Claim.attempts` remains a per-claim tally for the reviewer. |
| **The claimant is told exactly where they stand** | Tries left, when a cooldown ends, how many cooldowns remain before manual review, and when the claim has gone to manual. The limits are published and the state is the claimant's own, so specificity discloses nothing. A generic message turns a typo into a support call. Times are shown in the tenant's zone if stored, otherwise UTC. |
| **An expired code's entry changes nothing** | `expires_at` decides expiry, so `code_hash` stays until the next start overwrites it. The entry is a `rejected` refusal and consumes no attempt, because a dead code cannot be guessed. |
| **The lock's moderation item and the unlock ship in PR 4 (done, §4.6)** | PR 3 sets `verification_locked_at` and flips to `manual`. `ModerationItem` is designed in PR 4 around disputes, its representative producer, with the lock as a second `item_type`. The operator unlock never touches `rejections` or `claim_blocked_at`. Rejected: emitting `moderation.queued` for an item that does not exist. #220. |
| **A resend supersedes the prior code** | Only the latest hash is valid, and `expires_at` restarts. The prior `OutboundMessage`, if still `pending`, has `expires_at` set to now in the same transaction, so a dead code is never sent after an outage. The link is a nullable `Claim.code_message`. Superseding grants no guesses, because the counters are on the pair. |
| **Sends are capped per pair, core-fixed** | At least 60 seconds between sends, and at most 5 per rolling 24 hours, counting the code at `submit`. Disabled during a cooldown and after the lock. Otherwise anyone can name an address and flood it from the operator's SMTP. Per-IP limiting (#210) does not protect the recipient, because IPs rotate and the pair does not. |
| **Verification events** | `claim.verification_started` on every start carries `claim`, `method`, `expires_at` and the masked `destination`. `claim.verification_failed` on every wrong entry and on a post-submit flip carries the after-state `claim`, the failed `method`, and `reason` (`wrong_code`, `cooldown`, `locked` or `ineligible`). It also carries `attempt` (1 to 5 in the pair's window) and `cooldowns`, both null for `ineligible`. Guard refusals emit nothing. |
| **The message: kind, subject, body** | `kind` is `claim.verification_code`. The subject is `Your verification code for {listing name}` and never contains the code, because `subject` survives body nulling. The plain-text body carries the site name, the listing name, the code, the expiry, "only the most recent code works", and the absolute verify URL. It carries no claimant-supplied text, since anyone can name another person's address and would otherwise write into mail from the operator's domain. |
| **#210 and #212 stay separate** | #210 needs its own ruling on trusted client IP behind the proxy, and rate-limit storage without Redis (settled in §4.8). #212 concerns `claim.submit`'s existing branches. PR 3 renders and tests its own new refusals. |
| **Claimant-facing times are UTC** | No time zone is stored on `Tenant`, so §4.4's "otherwise UTC" is the branch that runs. Nothing else needs a zone field yet. |
| **No absolute base, no link line** | When `has_absolute_base(tenant)` is false, the message omits the verify link rather than carrying a relative path that no mail client can follow. The claimant is already on the verify page: submit redirects there whenever the method is `domain_email`. |
| **Submit during a cooldown or a spent send cap still creates the claim** | No code and no message are sent. The verify page shows when a send becomes possible. The inner start function returns "not sent" and never raises for these, so `claim.submit` concludes `applied`; only the `claim.start_verification` wrapper concludes them `rejected`. A lock at submit flips the claim to `manual`, and a blocked pair is rejected. |
| **Resend is its own POST-only route** | `claim/<claim id>/verify/resend/`, so each view calls exactly one command. |
| **Verify and start lock the guard row, then the claim, before any check** | Found in plan review: checking claim state before taking the lock let a parallel correct entry and wrong entry both pass on stale state. Verify refuses in the order status, method, verified, locked, cooldown, no active code, expired, so the reason always names the real state. |
| **The submitted page names the real reason for a flip** | The reasons are no eligible website, address not at `@host`, a locked pair, and, from §4.5, email verification unavailable. Found in the browser pass: a locked pair was being reported as an address mismatch. |

New subsection. #121 rulings.

| Decision | Reasoning |

Moving `smtp.username` and `storage.access_key` into `Secret` is #224; recording settings changes in the command log is #225. |

| **TLS mode is `smtp.security`: `none`, `starttls` or `tls`** | It replaces the `use_tls` boolean, which could not express implicit TLS on port 465. A data migration maps `true` to `starttls` and `false` to `none`; it is plain dict manipulation, idempotent, and imports no live code. The sender reads only the new key, and `tls` uses `smtplib.SMTP_SSL`. The port is pre-filled with 587; the help text gives 465 for `tls` and 25 for `none`. Rejected: a read-time fallback to `use_tls`, which keeps two shapes forever. |
| **Both TLS modes verify the certificate; credentials never go in the clear** | `starttls()` and `SMTP_SSL` both take `ssl.create_default_context()`. A bare `starttls()` uses the stdlib's unverified context, so certificates were not being checked. A username with `security` `none` is rejected by the form and by `update_tenant_settings`, and the sender treats it as unconfigured rather than authenticate in the clear. |
| **The from address is a pre-fill, not a send-time default** | The form's initial value is `noreply@` plus `primary_domain` verbatim, blank when the tenant has no domain. An empty stored `from_email` stays unconfigured. The mangled address in #121's first comment was typed or autofilled; no code produced it. |
| **Mail availability is one predicate on the capability** | An `email.send` provider exposes `available(ctx) -> bool` (an `AdapterContext`, §4.12), meaning configured, not reachable. The sender's own unconfigured check calls it, so the drain's `CapabilityUnconfigured` path, the admin banner and `claim.submit` agree, and claim eligibility, the banner and the drain never read `settings["smtp"]`. Core's configuration surface -- the form, the settings validator and `setup_state` -- does read and write that key, as it does `storage` and `claim_verification`; it never uses it to decide whether mail can be sent. Core's helper returns false when no provider is registered. Transient outages still queue and retry. |
| **`domain_email` flips to `manual` when mail is unavailable** | A fourth ineligibility reason beside §4.4's three, checked before create through the same path and re-checked by `claim.start_verification`. The submitted page says email verification is unavailable. Rejected: allowing it, which tells the claimant a code was sent that never will be and burns their send cap on resends. Rejected: refusing it at configuration, which makes core read `settings["smtp"]`, misses an unregistered provider, and breaks when block 5 replaces the sender. |
| **The settings page has no superadmin bypass** | It is gated by `tenant_admin_required` at the top role and nothing else. `is_superadmin` is installation-scope authorization and no other `/admin/` view honours it, so one credentials page doing so would be a precedent set by accident. A superadmin with no membership on a tenant gets the same 404 as anyone else; the console can mint one. Rejected: the "plus superadmin" this section first recorded. |
| **Migrating `use_tls` can leave a tenant unconfigured** | A tenant that had a username and `use_tls` false becomes `none` plus a username, which the sender treats as unavailable, so its mail stops and the banner appears until an admin picks STARTTLS or TLS. It previously sent plain AUTH. The migration prints how many tenants this affects and emits no `tenant.settings_changed`. `starttls` now verifies certificates, so a self-signed relay also fails, with a retried error and no opt-out. |
| **The stored password is never sent to a new host** | A host change with a username set and a blank password is a form error and an `InvalidTenantSettings` from `update_mail_settings`: "re-enter the password". Removing the password with the checkbox is accepted, since nothing is then sent. A stored secret with no stored host, which Skip can leave behind, counts as a change. The check lives in the service and form, not in `_validate_smtp`, because a value-only validator sees neither the stored host nor whether a password arrived. Skip deletes the stored password. |
| **Every flip to `manual` clears the code and expires the pending message** | All reasons: `code_hash` is cleared and a still-`pending` `code_message` has `expires_at` set to now, in the same transaction, exactly as a resend's supersede does. Otherwise a code queued before mail went down is delivered when it returns, for a claim whose method is now `manual`. Submit's own flip has no code yet; the verify lock flip and `claim.start_verification`'s flip go through the shared helper. The message stays `pending` for the drain to expire. |
| **`mail_unavailable` folds into `ineligible`, ranked above the address** | `claim.verification_failed` keeps its four reasons; a fifth would be a spec change. On the submitted page the order is no website, locked pair, mail unavailable, address not at the host, because fixing the address cannot help once mail is down. The copy is read from the claim's stored `review_reason` (§4.6), not recomputed, so a claim submitted while mail was down says so even after mail is configured. |
| **Skip stores an empty `smtp` block** | `setup_state` counts the step done once the `smtp` key exists, and the sender reads an empty host as unconfigured, so `{"smtp": {}}` needs no other change. §4.3's pending-row rule governs anything queued meanwhile. |
| **The unconfigured-mail banner shows on every tenant admin page** | Shown to all staff while `available` is false. The link to the settings page is shown only to roles that can edit it. |
| **No provider presets** | SES hosts are per region and Gmail needs an app password, so a static host and port list is wrong on day one and rots. The port help text covers the three modes. |

## §4.6 — Claim review

New subsection. Claims PR 4a rulings: manual review, approval, rejection, disputes and the moderation queue. The operator notification for claims entering manual review (#218) is PR 4b.

| Decision | Reasoning |
| --- | --- |
| **Claim review ships as 4a and 4b** | 4a is the models, the four operator commands, approval on verify-success, the dispute, lock and block items, the anti-hijack notice and the admin queue, backend and UI together. 4b is #218, the operator mail and its throttle (the four rows after "The review pages"). Ownership moves in 4a, so the §9.4 notice ships with it. |
| **A correct code on an unowned listing approves in the same transaction** | `claim.verify` sets `verified_at` and, in that transaction, calls the one approval helper. The claim's `result_event_id` is the `claim.approved` event. On an owned listing it disputes instead. On a suspended listing nothing moves: the claim stays open with `verified_at` set and is reviewed by hand. This supersedes §4.4's "records success and stops". |
| **A disputed claim may verify its email, and a code never approves one** | A `domain_email` claim submitted on a claimed listing was sent a code and then made unenterable by the status guard. `verify` and `start_verification` now accept `disputed`. A correct code records `verified_at` and nothing else: it is evidence for the reviewer, never a decision. The §4.4 "dispute on an owned one" at verify-success is therefore reachable only when the listing is claimed between submit and verify. |
| **Approving one claim rejects the other pending claims, by the system** | Keeps the 2026-09-11 ruling. The losers are `rejected` with `decided_by` `system` and reason "Another claim for this listing was approved.", their codes retired. They do not count toward the three-rejection block: no judgement was made on the claimant. Each loser is mailed the rejection by the same producer and with the same seven-day deadline as `claim.reject`, with that reason and a line pointing at the claim form to dispute the approved claim, since more information will not change it. Disputed claims are not losers and stay in the queue. The losers are locked with `skip_locked`, because `claim.verify` takes claim then listing and approval takes listing then losers; a claim held by another transaction is skipped, stays pending on the now-claimed listing, and is disputed by its own verify or by an operator's approval. Rejected: turning the losers into disputes. |
| **`Listing.owner` is the fact, `status` mirrors it, and one function writes both** | #48. `_assign_owner` in `directory/claim_review.py` is the only assignment to either field, reached from `_approve_claim`, which operator approval and code verification both call. `OwnerWriterTests` parses every non-test module and fails if anything else assigns `owner` or `owner_id`. A partial unique constraint allows one `approved` claim per listing. Rejected: a `CHECK (status <> 'claimed' OR owner_id IS NOT NULL)`, which collides with `owner` being `on_delete=SET_NULL` and waits on how erasure will work. |
| **A transfer supersedes the old claim** | Approving a disputed claim on an owned listing needs an explicit `transfer` confirmation. The previous approved claim moves to the new `superseded` status before the new one is approved, so the partial unique holds at every instant. No event exists for that move, so `listing.owner_assigned` carries `previous_owner_id` and `claim.approved` carries `transfer`. Approving a pending claim on a listing claimed in the meantime moves it to `disputed` and concludes `applied`; it never approves. |

A role below the requirement concludes the command `blocked`, not `rejected`. Nothing in this section gives a superadmin a bypass. |

The rejection reason is mailed to the claimant, because §9.6 relies on it to tell them what was missing. The command log carries the claim id and `manual_method_used`, never the notes or the reason. Operator commands set `actor.type` to `admin` for an active admin membership and `staff` below it (spec §4.4). |

A claim approved by its code keeps `domain_email`, has no `decided_by`, and its `claim.approved` carries a `verification` block in place of `manual_verification`. |
| **Unlock resets the verification counters, never the rejection counters** | `claim.unlock_verification` clears `verification_locked_at` and resets `cooldowns`, `wrong_entries` and `cooldown_until`; without that reset the next cooldown would re-lock the pair at once. This closes #220. |

## §4.7 — Worker tick jobs

New subsection. The #180 registry ruling and the jobs queued behind it (#132, #159, #193, #213), plus §11.2 payload nulling.

| Decision | Reasoning |
| -------- | --------- |
| **The tick registry is an instance, built by one composition root** (#180) | `audit.worker.jobs.build_tick_registry` is the only place that knows which jobs a worker runs; `run_worker.handle` calls it and hands the result to the loop. There is no module-level list and nothing registers at import time, so a second `handle()` in a process inherits nothing and no job outlives the `Command` whose stream it was bound to. A repeated name **raises** — silently ignoring it is what kept the first registration alive. |
| **Cadence belongs to the job's registration, not to the pass** | `run_due` runs every worker pass and each job declares `every`. `last_run` is stamped when a job is *attempted*, success or failure, so a job that raises waits out its cadence instead of being retried once a second. In-memory only: a restart runs every job once, which is safe because every job is idempotent. |
| **A tick job does bounded work and says whether there is more** | The tick shares a thread with the outbox and mail drains, so an unbounded job delays a claim-code email behind it. A job does at most one chunk per call and returns `TickResult(more=True)` while backlog remains; the job stays due and the worker does not idle. The CSV import already worked this way (`ROWS_PER_PASS`). |
| **`now` is required and keyword-only on every job** | One clock value per pass, threaded through. A test asserts it for every registered job; nothing in a job reads the clock. |
| **Tick failures are reported, not counted** | `worker_pass` writes each failed job to the worker's stderr. A retention job that has failed for a month is a compliance failure nobody was told about. |
| **The reindex drain resumes from a cursor** (#132) | `SearchReindexJob.cursor` is the highest listing id recomputed. A large marker is drained 200 listings a call across ticks and survives a restart. Only the marker being drained is stamped `done_at` — the command this replaced stamped every pending marker after a snapshot and lost any written in between. `rebuild_search_index` runs the same drain by hand; `--all` stays manual, since nothing writes a whole-tenant marker for a `search_config` change. |
| **Sitemaps are precomputed per tenant, change-detected by fingerprint** (#159) | Hooking every listing publish, unpublish and category write would couple the services to the worker. Each tick computes a cheap aggregate fingerprint per tenant (published count, `max(updated_at)`, id sum, listing-category pair sum, category and type routing fields, the absolute base) and renders **one tenant per call** only when it differs, at most once every five minutes per tenant — a bulk import must not cost a 50,000-URL render per row. Files go to the tenant's storage as a generation directory plus a `current.json` pointer written last. The views serve the stored file and fall back to live generation only for a tenant with no usable artifact (a cloud-storage tenant, #150, or before the first tick); the generated bytes are identical either way. An unverified domain has its artifact removed, per §4.1. |
| **Nulling a payload to `{}` with a stamp, not to `NULL`** | `OutboxEvent.data` is `NOT NULL` and the envelope always serialises a `data` object. `payload_nulled_at` separates "nulled" from "never had one". Nulled at 90 days from `created_at`, and only when nothing is left to deliver: the event is past fan-out and has no `pending` delivery. Dead letters are not exempt (§4, above). |
| **Payload nulling is the one permitted rewrite of a concluded command-log row** | Spec §11.2 says both "a concluded row is never rewritten" and "payload nulled at 90 days". The payload is a second copy of personal data, so the retention obligation wins, and it is the *only* exception: the `command_payload_retention` job sets `payload` to `NULL` and touches nothing else on the row — not the outcome, the problem, the timestamps or the result event id. A row whose command threw mid-apply (no `concluded_at`) is nulled on the same clock. The database does not enforce the rule (the app role holds `UPDATE`); a test asserts every other column survives. The spec wording is raised separately. |
| **`to_address` is nulled only on a terminal row** | A `pending` row is still going to be sent; the drain must never find its address gone. |
| **Retention sweeps run daily** | `import_pre_image_retention` (500 rows a call), `outbound_address_retention`, `event_payload_retention` and `command_payload_retention` (1,000 rows a call), each oldest-first. Window is strictly older than 90 days. |

## §4.8 — Rate limiting

New subsection. #210, spec §9.4. Operator login stays unthrottled (spec §15.6); there is no public API or review endpoint yet. The lead form is limited in §4.10 with the same machinery.

| Decision | Reasoning |
| -------- | --------- |
| **Four claim commands are limited, per tenant, by IP and by claimant email** | `claim.submit`: per IP 5 per 10 minutes and 20 per 24 hours; per email 5 per 24 hours. `claim.verify`: per IP 30 per 15 minutes. `claim.start_verification` (resend): per IP 10 per hour; per email 10 per 24 hours. The numbers are core-fixed constants in `directory.claim_limits`, not tenant settings, for the reasoning §9.5 and §9.6 give for their own limits. Every key is scoped to the tenant, so one directory's traffic never throttles another. |
| **"Per account" means the claimant's email** | Claimants have no accounts; a `DirectoryUser` is minted by the submit. The email is also the recipient of the code, which is the one thing a per-IP limit cannot protect (§4.4, "Sends are capped per pair"). **The consequence is accepted and named: anyone can spend a victim's per-email budget by naming their address, so a victim can be kept from submitting a claim for up to 24 hours.** The attacker gains nothing but the delay, and the victim has the manual path and another address. A budget that ignored the address would leave the recipient unprotected. |
| **Verify and resend are limited by IP beyond what §9.4 asks** | The per-pair guard already bounds guesses on one pair; the IP limits bound what one address can do across many pairs. Resend is also limited per email, because a victim can be named on many listings and the per-pair cap is per listing. The guards are untouched and independent. |
| **Counters are rows in Postgres, in autocommit** | `rate_limit_counters`, unique on `(tenant, rule, subject_hash, window_start)`, incremented by one atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING`. No Redis, no cache backend, no new dependency. The write commits on its own, outside the command transaction, so a count survives the rollback of the command it guards — the reasoning §11.2 gives for the command log — and `check` refuses to run inside an open transaction. |
| **Windows are fixed, not sliding** | A client can burst to twice a limit across a boundary. These are blunt anti-abuse limits in front of precise per-pair guards, and a fixed window is one row and one statement. |
| **The subject is stored as a keyed hash** | An IP is personal data. `salted_hmac` over Django's `SECRET_KEY` with SHA-256 — the mechanism `directory.claims.hash_code` already uses, for the same reason — over `(tenant, kind, value)`. IPv6 is reduced to its /64 first, because one subscriber commonly holds a whole /64 and per-address would be no limit. Rows are pruned by the hourly `rate_limit_prune` tick job once their window began more than 48 hours ago; a window is at most 24 hours. |
| **The limiter runs inside the command, ahead of the command log** | The service functions call it, not the views, so a future caller cannot skip it. It runs after the submit's payload is normalised (the email key is the normalised email) and before `log_received`. Checks stop at the first refusal, so a request already refused on its IP does not spend a victim's per-email budget. |
| **A refusal is logged once per window, as `blocked`** | Spec §11.2 puts blocked attempts in the command log. One row per refused request would let a flood write the log without bound, so the row is written only for the hit that first crosses a limit in a window (`count == limit + 1`); the counter holds the volume. No event is emitted: nothing changed that another system cares about. |
| **A refusal is a 429 with `Retry-After`, stating the wait and nothing else** | The page is the form or verify page that was asked for, with the input kept and "Too many attempts. Please try again in N minutes." Which rule fired is not shown. A `GET` is never limited, and `GET /search/` stays unlimited. |
| **`ip` is required, and nullable, on verify and resend** | `submit_claim` already took `ip`. A caller with no client address (a management command, a test) passes `None` and the IP rules are skipped; the email rules still apply. Required, so a view that forgets it fails loudly instead of silently dropping the limit; each view has a test that proves its limit trips. |
| **The client's address is `REMOTE_ADDR` unless a trusted proxy says otherwise** | `OSDS_TRUSTED_PROXIES`, comma-separated addresses or CIDRs, empty by default and validated at boot. Only when `REMOTE_ADDR` is inside it is `X-Forwarded-For` read, from the right, skipping trusted hops; the first untrusted address is the client. That is safe against a proxy that appends to a client-supplied header and against a client that prepends fake entries. Without it the header is never believed, because a client writes it. The consent record's IP uses the same resolver (it recorded the proxy's address behind one). |
| **A misconfigured proxy is a warning, not a switch** | Behind a proxy with `OSDS_TRUSTED_PROXIES` unset, every visitor looks like the proxy and the per-IP limits act site-wide. The resolver logs one WARNING per process when a private, non-loopback peer sends `X-Forwarded-For` with no trusted proxies configured. It does not disable the limit (an unnoticed switch-off) or fail closed (a site-wide outage); the README says how to set it. `SECURE_PROXY_SSL_HEADER` has the same trust problem and is its own issue, resolved in §4.13. |
| **Spec §15.6 stays open** | The claim submission limits the spec lists as "settled in §9.6" are decided here: §9.6 sets code-entry and rejection caps per pair, and §9.4 asks for per-IP and per-account limits without numbers. Public API, review and operator-login limits are not decided by this section. |

## §4.9 — Owner sign-in

New subsection. The owner's emailed sign-in link, their session, the dashboard, and what an owner may edit and upload. Built in two steps and shipped as one PR. The spec's open §15.4 (owner dashboard scope) is ruled below.

| Decision | Reasoning |
| --- | --- |
| **An owner is a user for whom `Listing.owner` currently points at them** | Not a user with an approved claim somewhere in history. Authorization is live: nothing about ownership is stored in the session, every owner route resolves the listing through `Listing.owner`, and a listing that is not the owner's -- never theirs, or theirs until a transfer -- is a 404, never a 403. A former owner loses the listing the moment ownership moves, with no session to revoke. |
| **The sign-in link is a 256-bit token, stored only as a SHA-256 digest** | `OwnerSignInToken`. The plaintext, `secrets.token_urlsafe(32)`, exists in the mail and nowhere else. A plain digest is enough because the token is high-entropy; §4.4's keyed hash exists to stop a dump reversing a six-digit code, which this is not. Lifetime is 12 hours, core-computed, from spec §4.3 and the #208 ruling; it does not take §9.5's bounds. The mail's `expires_at` is the token's. |
| **Following the link spends nothing; a POST from the confirm page does** | **Deviation from spec §4.3's "following it opens a session."** A mail scanner follows links, and a link that signs in on GET is burned before its owner reads the mail. The link opens a page with one button; the POST spends the token and opens the session in one transaction under `select_for_update`. The page and every refusal are sent with `Referrer-Policy: same-origin` and `Cache-Control: no-store`. `same-origin`, not `no-referrer`: with `no-referrer` a browser sends `Origin: null` on the confirm page's own form POST and Django's CSRF origin check refuses it (found in the browser pass). `same-origin` still sends no referrer to any other site, so the token URL never leaves this one. Unknown, expired, used and foreign links are the same page, 400. |
| **Only the latest link works** | A new link expires every earlier unused one and kills its mail if it has not gone out, the way a code resend does. |
| **A link is sent only to an address that owns a listing, and nothing in the response says whether it did** | The sent page is the same for an owner, a stranger, a claimant with only a pending claim and a throttled owner: status, redirect and body. A different response would be an oracle for which addresses own a listing, the invitation rule of spec §4.4 again. The command log records the reason (`not_an_owner`, `too_soon`, `hourly_cap`, `unavailable`) and never the address, the token or the user. |
| **Sign-in is unavailable without mail that can be sent and a verified domain** | The link is the whole message, and without a verified domain it is a relative path no mail client can open, so the page says sign-in is unavailable rather than send something useless. |
| **Two limits: per IP through `audit.ratelimit`, and per account from the token rows** | #210's helper, following `claim_limits.py`: `owner.request_signin` is 10 per 15 minutes and 40 per 24 hours per IP, by `osds.client_ip`, refused as a 429 with `Retry-After` and one `blocked` command-log row per window. The account limit is 3 links an hour and 60 seconds apart, counted from `OwnerSignInToken.created_at` -- it limits mail sent to one real owner, which is exactly what those rows record, so it has no table of its own. A throttled owner gets the ordinary sent page. Exchanging a link needs no limit: it is 256 random bits. |
| **The owner's session is its own: a table, a cookie and a guard** | `OwnerSession` and the `osds_owner` cookie, never `request.user` and never the Django session. An operator session cannot satisfy `owner_required` and an owner session cannot satisfy `tenant_admin_required`; one person may hold both, and neither signing in nor signing out of one touches the other. The Django session cannot give the owner's semantics anyway: `SESSION_COOKIE_AGE` is an absolute cap, not an idle timeout. The guard runs on the owner routes only, not as middleware, so a public page costs no query. |
| **A session ends after 12 hours idle and after 30 days regardless** | Spec §4.3 gives only the idle timeout; the 30-day absolute cap is added to bound a stolen cookie. `last_seen_at` moves at most once a minute, so reading a page is not a write. An expired session is deleted when it is seen. |
| **The cookie** | Host-only, HttpOnly, `SameSite=Lax` (the sign-in arrives by a top-level navigation from a mail client), `Secure` by `OSDS_SECURE_COOKIES` like the operator cookies, path `/owner/`, `max_age` 30 days. Each session is looked up by the digest of its cookie value and scoped to the request's tenant, so a cookie means nothing on another directory. |
| **Sign-out ends one session or all of the owner's on that directory** | `owner.sign_out`, POST only, behind CSRF. |
| **No event is emitted for sign-in or sign-out** | Spec §3.3 has no such event, and a sign-in is not a state change another system acts on, like mail sending (§4.3). The command log is the record; its payload carries nothing identifying. |
| **Expired links and sessions are pruned by the tick** | `owner_auth_prune`, hourly, in `audit.worker.jobs`: links expired for more than a day and sessions expired or idle for more than a day past their idle limit, 1,000 rows a table a call, `more` while there is backlog. Kept a day past their end so "my link did not work" can be diagnosed. #88 is the same gap for operator sessions. |
| **Owner mail is one kind, `owner.signin_link`** | The link, the site name and the expiry. It carries no name, listing or claimant text: the user row's name was supplied by whoever first claimed with that address. |
| **The `owner` slug is reserved** | `/owner/` routes sit ahead of the public catch-all, so a category or listing slug of `owner` would be shadowed. It joins `RESERVED_SLUGS`; an install that already holds one needs it renamed, and only dev databases do. |
| **What an owner may edit (spec §15.4, ruled)** | Free: description, phone, public custom fields and media. Operator-only: name, slug, categories, website, email and address. The contact fields feed defences: the website's host decides `domain_email` eligibility and the listing email is where the anti-hijack notice goes, so an owner able to rewrite them could defeat a genuine owner's later dispute. Name and slug change identity and URLs; categories change placement. A forbidden key is refused, not silently dropped (spec §7.1). A "request a change" queue is a later `ModerationItem` type. |
| **Leads are on the dashboard as a link** | The dashboard links to the owner's leads page (§4.10), with the count of non-spam inquiries. The billing banners of spec §6.5 wait on billing. |
| **Email is the identity, and that is accepted** | Ownership follows the mailbox. An address reassigned to a different person -- a departed employee's -- signs the new holder in as the owner. That is inherent to the design the spec chose (§4.3), where a link re-proves mailbox control on every entry instead of a stored credential. An operator's recourse is the dispute and transfer path of §4.6. |
| **The token is in the URL, so unused tokens reach access logs** | gunicorn logs the path. Single use and a 12-hour life bound it, and a used or expired token in a log is dead. Redacting paths belongs with #179's logging configuration. |
| **An owner's edit is `listing.upsert` with the owner as actor** | `owner_update_listing` is a thin guard over `upsert_listing`, which stays the one write path for every population route. The payload is built from an allowlist (`description`, `phone_e164` and `custom_fields`), pinned to this listing's id, with `enforce_required` on ("enforced on create and on owner edit", spec §4.5). Every free field is sent on each save, so a cleared input is an explicit `null` (spec §7.1). Events and the command log say `actor.type` `owner` with the user's `usr_` id; `source` is only read on create, so an edit never rewrites provenance. |
| **A forbidden key is refused as a rejected `listing.upsert` row, not dropped** | An operator-only key (name, slug, categories, website, email, address, and the payload's `location` and `contact` containers) is refused by name, and so is any key the write path itself rejects (`tier`, `status`, `visibility`, `media`, `id`) or an unknown one. The whole change is refused, never the forbidden key alone: a free edit beside a forbidden key does not land. The refusal is written to the command log even though no upsert ran, with the keys and never the values; someone who does not own the listing is `blocked`, the rest `rejected`. The page enforces the same rule against a crafted POST that names a forbidden field, which Django would otherwise ignore. |
| **Only a type's public custom fields are the owner's** | `public` false means admin-only (spec §4.5), so an admin-only field is refused like an operator-only core field, and an unknown key is refused too. |
| **The ownership check and the upsert are two transactions** | `upsert_listing` requires autocommit, so the live `Listing.owner` check runs just before it, not inside it. An owner who loses the listing in the instant between the two can land one last edit: an ordinary `listing.updated` the new owner can see and revert. Accepted. |
| **Media goes through the existing media service** | `attach_media` and `detach_media`, with the owner as actor; the bytes are validated and stripped there. `MediaAsset.uploaded_by` points at an operator, so an owner's upload leaves it null, and the actor on the `listing.updated` event is the record. As on the operator path, media writes emit `listing.updated` and have no command-log row of their own. |
| **The leads page is the owner's inquiry list** | `/owner/leads/` is behind the owner guard; lead capture replaced the placeholder (§4.10). |

## §4.10 — Lead capture

New subsection. Spec §3.3 `lead.*`, §7 `lead.create` and `lead.markSpam`, §9.0. Owner sign-in and the owner's leads page are §4.9 and the owner-edit PR, not here.

| Decision | Reasoning |
| -------- | --------- |
| **Lead forms are off until an admin turns them on** | `settings["leads"]["enabled"]`, default false, set from `/admin/settings/leads/` at the admin role and validated in `update_tenant_settings`. A disabled directory 404s the form and its confirmation page, so it exposes nothing. The consent wording below has had no legal review and no UI publishes a new version, which is the other reason to default off. |
| **The form is `/lead/<listing id>/`, linked from a published listing's page** | Server-rendered, no JavaScript, never cached, `X-Robots-Tag: noindex`. `lead` is a reserved slug. `source_page` is worked out from the listing, never taken from the visitor. The confirmation page is stateless and takes no lead id, so nothing can be looked up with it. |
| **Two traps, then the limits** | A hidden field no person fills, and a signed render time no person beats (under 3 seconds). A trapped submission gets the ordinary confirmation and creates nothing, so a bot learns nothing; it counts against its own IP rule (3 an hour) and is refused like any flood once that is spent. A missing, forged or over-2-hour token is a form error, not a trap: a person can be slow. |
| **`lead.create` is one command, and mints no user** | Same shape as `claim.submit`: autocommit only, normalise, rate-limit, `log_received`, one atomic apply, `log_conclude`. The atomic block writes the `Lead`, its `Consent` row, `lead.captured` (spec §3.3 shape) and, unless the lead is spam, the notice, so a notice commits with the lead that caused it. The actor id is `""` — never an email (#219) — and no `DirectoryUser` is created, because only `claim.submit` does that. The command-log payload is the normalised input, personal data included, and is nulled at 90 days by the existing job. The spec's adapter-side `lead.create` is the same command with another caller. |
| **A refusal is logged where the claim flow logs it** | Missing or declined consent, a disabled tenant and an unpublished or suspended listing conclude `rejected`; a rate-limit refusal concludes `blocked`, once per window (§4.8). A command that throws mid-apply leaves its row unconcluded (§11.2). |
| **A repeat is not a second lead** | The same message from the same address to the same listing inside an hour returns the first lead, concludes `applied` with `problem: {"duplicate_of": …}`, and creates no row, event or notice. A double-click must not mail an owner twice. |
| **Consent is one channel, `contact_by_business`, and it must be granted** | A lead that cannot be answered is pointless, so a decline is rejected like an omission and logged; this is narrower than claims, where each channel may be declined. The wording is `ConsentText` key `lead-consent`, v1, seeded lazily like the claim wording and recorded server-side as `lead-consent-v1` — never a client-supplied version. The IP is stored only if it parses (`osds.client_ip.storable_ip`), so a record never fails to save on junk. Counsel review of the wording is tracked in its own issue. |
| **Limits** | Per tenant: `lead.create` per IP 6 per 10 minutes and 30 per 24 hours, per email 10 per 24 hours; the trap rule 3 per hour. Core-fixed, in `directory.lead_limits`, enforced inside the command as in §4.8; `ip` is required but nullable. The business is protected from a flood by the notice throttle, not by a per-listing cap, because a cap would let an attacker switch one listing's form off. |
| **Spam is a score, not a classifier** | A fixed-weight heuristic (links, shouting, repeated characters, a link or address in the name) stored in `spam_score`. At 0.8 or above the lead is stored, marked, announced with `lead.marked_spam` (`by: "system"`, with the signals) and told to nobody. The threshold is a constant to tune. A moderator can read it and mark others (`lead.mark_spam`, one-way). |
| **Delivery: the owner if there is one, otherwise the staff who can act** | A listing with an owner: the owner is emailed "N new inquiries", with a link to `/owner/leads/` when the tenant has an absolute base, TTL 7 days. A listing with no owner: active memberships at EDITOR and above, a link to `/admin/leads/`, TTL 48 hours. **An unclaimed listing's own address is never mailed** — it was imported, not given. **The visitor is never mailed**, because anyone can name an address (§4.4, "Sends are capped per pair"). No notice carries visitor-supplied text: anyone can write anything into the form, and a notice goes out from the operator's domain. |
| **Notices are throttled per recipient and count what they skipped** | A recipient is mailed at most once every 15 minutes, derived from recent `OutboundMessage` rows with no table of its own, as the claim operator notice is. The next notice counts every non-spam lead since the previous one, so a throttled lead is deferred, never lost. The `lead_notice_flush` tick job (every 60 seconds, at most 200 notices a call, `more` while a backlog remains) announces a deferred lead once the window has passed, through the same routine, so a lead that no later lead follows is still announced and nothing is announced twice; a lead older than the notice lifetime is not. Reading them is the owner's leads page, which ships with the owner-edit PR; until then an owner is told and has nowhere to read. |
| **`lead.delivered` and `lead.delivery_failed` are not emitted** | Sending mail emits no event (§4.3), so core has no point at which it could know. `Lead.status` stays `captured`. Revisit with a delivery channel that can report. |
| **The owner reads their inquiries at `/owner/leads/`** | Behind `owner_required`: the non-spam leads on listings the owner holds, newest first, 50 a page, with the visitor's name, email, phone and message in full — the owner is who they were sent to — escaped, and `noindex`. Ownership is resolved live on every request, so another owner's leads can never appear and a listing that changes hands takes its leads with it. Every view writes an `AccessLog` row (actor type `owner`, resource `owner_leads`) whose `extra` names the page and the lead ids shown, so the log can say exactly which inquiries an owner was shown. Spam-marked leads are not shown. Spec §6.4's gating of lead access by tier is not applied: billing does not exist yet. |
| **Operators read leads in the admin, and the personal-data cut is manager** | `/admin/leads/` and a lead's page at moderator: the message in full (a moderator cannot judge spam without it), the address and phone masked, no consent record. Manager and above see everything, matching spec §4.4: the cut between 3 and 2 is money and personal data. Support sees nothing. Export is not built. |
| **The access log has its first writer, and its retention rule** | Every lead detail view writes an `AccessLog` row, masked or not, with the rank it was served at; the list page does not. Spec §11.2 keeps the log two years in its own store, so the `access_log_retention` tick job deletes rows strictly older than 730 days, in bounded chunks, daily. |
| **An imported listing that carries a lead cannot be rolled back** | `Lead.listing` and `Consent.lead` cascade, and a lead's consent is evidence (§9.0). The precondition that already refuses a listing carrying a claim now refuses one carrying a lead too (`created_listing_has_leads`), for the reason in §4.2. |
| **Not in this section** | PII redaction for adapters (invariant 8) landed in §4.12 with the webhook adapter. An erasure path and a consent-wording editor are each their own issue. |

## §4.11 — Billing: tiers and entitlements

New subsection. Block 4 rulings. Built as three PRs: **PR 1** (merged) is tiers, the entitlement state machine, comps, revoke and override, the clock-driven transitions and the operator pages, with no payment code; **PR 2** (the last rows of this table) is the payment seam (`entitlement.reportPayment`, checkout, cancel, the inbound route, `AdapterContext`, the owner's billing pages and mail); **PR 3** is the Stripe adapter. Where the spec and the code disagree below, `docs/spec/` is unchanged and this section is the ruling.

| Decision | Reasoning |
| --- | --- |
| **One entitlement per listing; no row means `none`** | `uniq_entitlement_listing`. The spec describes one record (§6.1), and history is the event log, not extra rows. The row is created by the first start or grant, which is why `none` is the absence of one. |
| **The state machine is data** | `billing.machine.TRANSITIONS` is the whole table: a key `(from, trigger)` is a legal move and anything else is refused with nothing written. `billing.tests.test_machine` drives every entry through `apply_trigger` and checks the landing status, the `entitlement.*` events in order, and `listing.tier_changed` against the spec §6.5 rule restated in the test; it also drives every pair *not* in the table. A transition added without a test cannot pass. |
| **Gaps G1-G9 in the spec's §6.3, defined** | **G1** an expired or never-purchased listing buys again (`entitlement.started`). **G2** a canceled owner resubscribes before the period ends and returns to active (`entitlement.restored`). **G3** cancelling from `past_due` skips grace and runs to the period end; cancelling from `grace` ends it at once, emitting `entitlement.canceled` and `entitlement.expired` (cause `canceled`). **G4** a refund in any paid state expires it. **G5** a comped listing that buys becomes active and the comp clears. **G6** an active renewal or tier change stays active, emitting only `listing.tier_changed` if the tier moves; a repeat failure while `past_due` or `grace` is counted and emits nothing. **G7** the adapter reporting a subscription ended outright expires it (cause `canceled`). **G8** a trial the payment adapter never reports on goes to `past_due` three days after `trial_ends_at`, with failure code `trial_unreported`. **G9** `entitlement.revoke` ends a comp: `entitlement.overridden`, `entitlement.expired` (cause `revoked`) and `listing.tier_changed`. |
| **The effective tier is the one place perks are decided** | Perks show in `trialing`, `active`, `past_due`, `canceled` before its period ends, and `comped`; `none`, `grace` and `expired` sit on the tenant's rank-0 tier, or on no tier if it has none (spec §6.5). `past_due` keeps full perks deliberately. |
| **`Listing.current_tier` has one writer** | `billing.entitlements._set_tier`, mirroring `_assign_owner` (§4.6). It emits `listing.tier_changed` whenever the effective tier moves, so no row can forget it or invent it: the clock rows (11, 15) emit it as well as their `entitlement.*` event. An AST test fails if anything else assigns `current_tier` or `current_tier_id`. |
| **The cause enums** | `listing.tier_changed.cause`: `purchase`, `upgrade`, `downgrade`, `grace`, `expiry`, `refund`, `comp`, `revoke`, `override`, `restore` (a payment that moves the tier is an upgrade or a downgrade by rank). `entitlement.expired.cause`: `term_ended`, `grace_elapsed`, `period_ended`, `comp_expired`, `refund`, `canceled`, `revoked`. The spec leaves both open. |
| **Spec §6.3 row 8: a refund emits both events, cause `refund`** | The spec lists only `listing.tier_changed`, while every other expiry also emits `entitlement.expired`. An adapter that listens for expiries should not have to special-case refunds. |
| **Core emits `billing.*` from `entitlement.reportPayment`** | The spec's §6 says an adapter "reports `billing.payment_succeeded`", while §8.3 says adapters never emit events. Core emits them, in PR 2, as the consequence of the command. |
| **Never-purchased listings are untouched** | The spec only hides a listing at expiry. A listing with no entitlement keeps whatever `current_tier` and visibility it has, in a tenant with or without a rank-0 tier; nothing here creates entitlements for them. |
| **Hidden by expiry, and unhidden on repurchase** | With no rank-0 tier an expired entitlement hides a published listing through the ordinary visibility path (`listing.unpublished`, reason `entitlement_expired`) and sets `hidden_by_expiry`. A later start or payment that returns it to a perk status republishes it only if the marker is set and the listing is still `hidden`: a listing someone moved to draft in the meantime stays where they put it. With a rank-0 tier an expired listing is never unpublished. |
| **Perks are opaque** | `Tier.perks` is stored and shown, and nothing interprets it. What the public page does today is the badge and the search rank, which already follow `current_tier`. A perk is a feature of its own and arrives with it. |
| **Dunning and grace run on core's clock** | Dunning is 14 days from the *first* failure (later failures do not restart it); grace is 30 days from the moment grace *began*, so a worker that was down never shortens it, and a late tick walks one step a run. The tick selects what looks due and `apply_trigger` re-checks under the entitlement and listing locks, so a payment that landed a moment earlier wins. Locks are taken entitlement first, then listing, always. |
| **Tick jobs** | `entitlement_transitions` every 5 minutes (rows 9, 11, 13, 14, 15 and G8; 200 rows a call, `more` while there is backlog) and `entitlement_renewal_notices` hourly (spec §6.6's T-10 `entitlement.renewal_due` for term entitlements, once a period). Terms are tied to slot pools, so today they cover an operator-set term; the owner mail rides with PR 2. Trial conversion and dunning recovery are payment outcomes the adapter reports, not tick work. |
| **Roles** | Tiers and pricing are the admin's (spec §4.4). Comps, revoke and override are the manager's, and a role below concludes the command `blocked`. A comp needs a tier, a reason and a future expiry if it has one; a slot-backed tier cannot be comped or created yet. The public page shows an ordinary badge for a comp and nothing says it is one. |
| **Operator commands are logged, the clock's transitions are not** | `entitlement.grant`, `entitlement.revoke` and `entitlement.override` follow the orchestrator shape with command-log rows carrying ids and never the reason. A tick transition is not a command anyone attempted; its record is the event it emits, with the system as actor. Entitlement events are subject to the entitlement's `ent_` id and `listing.tier_changed` to the listing. |
| **Tier configuration** | `tier.create/update/delete` emit `tenant.settings_changed` with a `/tiers/{key}` pointer, like listing types. Rules: lowercase key (immutable), rank 0 or more, rank 0 is the free fallback and cannot be purchasable, a purchasable tier has a price above zero in integer minor units, a three-letter currency and a billing interval (`month` or `year`; fixed terms arrive with slots), a trial is 1 to 90 days, `uses_slot` is refused for now. Enforced in the service and, for the two structural rules, by `CheckConstraint`. A tier cannot be deleted while an entitlement or a listing's badge points at it. The admin page says so at the point of configuration when a tenant has no rank-0 tier, because expiry then hides listings (spec §6.4). |
| **Payments need a verified domain over HTTPS** | Stripe will not call a plain-HTTP webhook, so an HTTP-only install cannot take payments. PR 2's availability predicate follows the one sign-in links use (§4.9): a sendable provider and an absolute base. |
| **A payment adapter is configured without core naming it** | CLAUDE.md invariant 1 forbids a vendor name in core, so the payments settings page cannot be a Stripe form in `tenants/`. PR 3 builds a generic adapter-settings form driven by the provider's own field list, storing config and secrets under the adapter's id. `AdapterContext` (config, a secret resolver, an allowlisted HTTP client, a clock) is brought forward from block 5 into PR 2, so the new adapter does not repeat #215. The Stripe adapter is stdlib only, with no SDK. `test_invariants` fails if a payment vendor is named anywhere in `directory/`, `tenants/`, `billing/` or `audit/`. |
| **PR 2 (the payment seam): what it builds, and what it does not** | Builds the `payments.checkout` and `payments.subscription` capabilities and the provider contract, the minimal `AdapterContext`, `entitlement.reportPayment`, `CheckoutAttempt` and `PaymentReceipt`, `billing.start_checkout`, `entitlement.cancel`, the inbound route, the generic adapter-settings page, the owner's billing pages with the §6.5 banners, and the owner's billing mail, all tested against a stub provider that lives in the tests. It names no vendor and has no network code; the Stripe adapter is PR 3. |
| **A provider returns data and core applies it** | `osds/adapter_api.py` is the whole contract: a provider exposes `available`, `settings_fields`, `create_checkout`, `cancel_subscription`, `portal_url` and `inbound`, and returns plain dataclasses (`CheckoutResult`, `PaymentReport`, `InboundResult`). It never calls a service function, writes a table or emits an event (spec §8.3). One provider object is registered under both capability names; `adapter_by_id` finds it for the inbound route. |
| **`AdapterContext`, brought forward from block 5 (#215)** | Config, a secret resolver, an allowlisted HTTP client and a clock, built by `osds/adapter_context.py`. Config lives at `tenant.settings["adapters"][adapter_id]`; secrets resolve tenant override then deployment (spec §8.1) under `"<adapter_id>_<key>"`, and a missing one is `SecretNotFound`, never core's `ConfigurationError`. Egress is allowlisted by exact hostname, HTTPS only, and redirects are not followed, since one to an unlisted host would otherwise pass the check. An adapter imports `osds.adapter_api` and `osds.adapters` and nothing else from core. The SMTP sender keeps its exception until block 5. |
| **`entitlement.reportPayment`: the report says what happened, core decides the tier** | The kinds are `checkout_completed`, `payment_succeeded`, `payment_failed`, `refunded`, `subscription_changed` and `subscription_canceled`. Each maps to one trigger on the §4.11 state machine, and the tier of a new purchase is the one core offered when it created the `CheckoutAttempt`, never the one the report names. Core emits every event: the `billing.*` money fact (subject the listing), the `entitlement.*` consequence and `listing.tier_changed`, each with the adapter's id as `origin` and as actor, which is what keeps an adapter from reacting to its own report. This is the resolution of spec conflict 1. |
| **Idempotent on the provider's event id, and acknowledged** | `PaymentReceipt` is unique on `(tenant, adapter, event id)` and is inserted first, in the transaction that makes the state change, so two simultaneous deliveries lose to the database, not to a race. A replay is a `replayed` outcome and a replay row in the command log. An event core cannot or need not act on -- an unknown listing or checkout, a tier core never offered, a move the state machine refuses -- is recorded `ignored` and acknowledged: the provider is told it arrived and does not retry what retrying cannot fix. A signature failure is 400, an unconfigured secret 503 and a database failure 500, because those retries can fix. The command log keeps the kind and the ids, never an address or a payment detail. |
| **A first invoice can arrive before the checkout completion** | Providers do not order their events. `payment_succeeded` for a listing with no entitlement, carrying a started checkout attempt, acts as the start; the completion that follows finds the entitlement already in force, is ignored, and the attempt is still marked completed (that write survives the rollback of the ignored one). |
| **`CheckoutAttempt`: a signed event cannot buy what core never offered** | Core creates the row, with the tier and a 24-hour expiry, before it calls the provider, and a completion must name an attempt for the same listing. The provider call is made outside any transaction so a network round trip never holds a lock; a provider failure marks the attempt `failed`, emits nothing and refuses with a plain message. `billing.start_checkout` refuses a listing that is not the owner's, is suspended, or already has a paid plan; a listing in `past_due` or `grace` is sent to the provider's card page (`use_portal`), because a second subscription would double-bill it. An expired, canceled or comped listing may buy. At most ten attempts an hour per owner, through `audit.ratelimit`. |
| **`entitlement.cancel` asks the provider first** | Core never marks a subscription cancelled while the provider would go on charging it: it calls `cancel_subscription` (at period end, or at once from grace per G3) and a failure, or a paid entitlement with no provider registered, refuses with nothing changed. An entitlement with no provider reference is cancelled without a call. The owner may cancel their own listing (live ownership); a manager may cancel for them. A comp is revoked, not cancelled. It emits `billing.subscription_canceled`. |
| **The inbound route** | `POST /_adapters/<adapter_id>/inbound/` on a tenant's host, so a webhook URL and its secret are per directory; `_adapters` is a reserved slug. CSRF-exempt, because the caller is a provider's server; the adapter verifies the provider's signature over the raw body, which core hands it untouched. Bodies over 256 KB are refused before the adapter sees them, and an unauthenticated route that does a signature check per request is limited to 300 a minute per address. |
| **The adapter-settings page is generic** | `/admin/settings/payments/`, admin only, built from the provider's `settings_fields()` so core never names it. Non-secret values are `tenant.settings["adapters"][id]`, written through `update_tenant_settings` (so `tenant.settings_changed` carries the config and never a secret; a validator accepts scalars only); secrets go to the secret store under the adapter's id. A blank secret keeps the stored one, an explicit clear removes it, a required secret cannot be left unset, and a refused save leaves no secret behind. The page shows the webhook URL, and says payments are unavailable until the directory has a verified domain. |
| **What the owner sees, per spec §6.5** | On the listing page and, for the warnings, on the dashboard: trialing "Trial ends in N days", active the plan and renewal date, past_due a persistent "Payment failed, update card" with a card link, grace "downgraded, restore it" with a restore link, canceled "Cancelled, active until {date}" with a way back, expired and none an upgrade prompt, and **a comped listing nothing at all**. Upgrade, cancel and the card link are POST (the link a GET redirect) routes under `/owner/listings/<id>/billing/`, each resolving ownership live. The page the provider returns the owner to promises nothing: the entitlement changes only when the provider's report arrives, so it says confirmation may take a moment. The locked-state lead summary waits on lead capture. |
| **The owner's billing mail** | Sent by `apply_trigger` in the transaction that moved the entitlement, to the listing's owner: a failed payment (until the dunning window ends), a downgrade (until grace ends), an expiry (seven days), a cancellation (until the period ends, else seven days). A cancel from grace sends one message, not two. A comp ending, a revoke and an operator override send nothing. The link needs an absolute base and is omitted without one. No claimant-supplied text. |
| **The vendor-name test now covers `osds/` too** | The composition root holds the seam and must stay vendor-free. A stub provider in the tests proves the whole path without one. |

Billing PR 3 rulings: the bundled Stripe adapter.

| Decision | Reasoning |
|---|---|
| **`adapters/stripe` is stdlib only** | `urllib` through `ctx.http` (so the allowlist, HTTPS-only and no-redirect rules apply) and `hmac`/`hashlib`. No Stripe SDK: the surface is five calls, and an SDK is a runtime dependency a human must approve. Allowlist `api.stripe.com`, nothing else. A test parses every module and fails on an import of `billing`, `directory`, `tenants` or `audit`; the only core imports are `osds.adapter_api`, and `osds.adapters` in `apps.py` to register. |
| **`osds/settings.py` may name the package** | `INSTALLED_APPS` must list `adapters.stripe`, as it lists `adapters.smtp`. The vendor-name test skips that one file; every other file in `osds/` is still scanned. |
| **Signature rules** | `Stripe-Signature` is `t=…,v1=…`: HMAC-SHA256 over `"{t}.{raw body}"`, compared in constant time against **every** `v1` (a rolled secret sends two) with no early exit, other schemes ignored, and a five-minute tolerance each way that is not configurable. A failure is 400 and the reason is never sent back. Nothing is looked up or reported for a body that has not verified. Stripe's documentation gives the header format and algorithm but no complete (secret, payload, signature) example, so the tests build the documented scheme independently with `hashlib` and pin two computed vectors; they are not Stripe-published values. |
| **The event mapping** | `checkout.session.completed` (subscription mode) → `checkout_completed`, with the period end read from the subscription, or its trial end; `invoice.paid` → `payment_succeeded`, except the $0 invoice that opens a trial (no money moved); `invoice.payment_failed` → `payment_failed`; `customer.subscription.updated` → `subscription_canceled` (cancel at period end switched on), `payment_succeeded` (switched off: core returns a cancelled listing to active only through a payment, G2), or `subscription_changed` (a price that is a configured tier); `customer.subscription.deleted` → `subscription_canceled` now; `charge.refunded` → `refunded`, only when fully refunded. `invoice.payment_succeeded` is deliberately unhandled: it duplicates `invoice.paid`. The report's event id is Stripe's event id. |
| **Our metadata or not ours** | The adapter stamps `attempt_id`, `listing_id` and `tier` on the Checkout Session and on the subscription, so every later event names the listing without a lookup. An event whose subscription lacks them was not created here and is acknowledged and ignored. A refund carries only a charge, so the listing is found through `GET subscriptions?customer=…` metadata. |
| **API-version drift is read, not pinned** | The account's API version decides event shapes. The invoice's subscription and metadata, and a subscription's period end, are read from both the older and the newer location. |
| **A lookup failure is a 503, an absence is not** | When an event needs a Stripe read and it fails, the answer is 503 so Stripe retries, and no receipt is written. A subscription that no longer exists (404 `resource_missing`) is ignored: a retry cannot fix it. |
| **The price is verified before the session** | Core shows the owner its own tier price; Stripe charges the Price. Before creating a session the adapter reads the configured Price and refuses if it is inactive or its amount, currency or interval differs. A mismatch would charge something other than what was offered. |
| **Price ids are one setting** | `settings_fields()` has no per-tenant context, so the price for each tier is one field, `tier-key=price_…, tier-key=price_…`. Secrets are `secret_key` and `webhook_secret`. |
| **`SettingField.pattern`** | An optional regular expression core checks before saving a typed value. The error names the field, never the value (it may be a secret), and a refused save writes nothing. It catches a pasted publishable key, or the wrong secret in the wrong box, at the form and not at the first webhook. |
| **Stripe errors carry type and code only** | `PaymentError` is `stripe <status> <type> <code>`: never Stripe's message, which can echo request parameters, and never a key. |
| **Cancel and the portal** | Cancel at period end is `cancel_at_period_end=true`; at once is `DELETE`. A 404 on cancel is success: the outcome asked for. A reference is validated as a `sub_` or `cus_` id before it is placed in a path, so a stored value cannot reach another endpoint. The portal link needs the customer id the adapter saved on the entitlement. |
| **Checkout is idempotent per attempt** | The attempt id is the `Idempotency-Key`, so a retried create after a timeout returns the same session. A trial is `subscription_data[trial_period_days]`; a card is always collected (spec §6.7). |

## §4.12 — The webhook adapter, redaction and the adapter runtime

New subsection. Invariant 8 (#238), the webhook adapter (spec §8.6, mvp-plan block 5), the adapter logger (#179) and the SMTP sender's move onto `AdapterContext` (#215).

| Decision | Reasoning |
| -------- | --------- |
| **Redaction is core's, at the drain, and an adapter cannot skip it** | `audit.redaction.redact` runs between `to_wire` and `subscriber.handle`, the only place an envelope reaches a subscriber (a test asserts `to_wire` has exactly one caller). The adapter receives the envelope already stripped and has nothing to forget to call. A withheld value is `null` where it was, and the envelope gains `redacted`, the list of paths withheld, so an adapter can tell "withheld" from "absent". The stored event is never touched. |
| **Two scopes, granted by the tenant's admin, never by the adapter** | `pii:contact` is who someone is and how to reach them: names, emails, phones, IP addresses, a listing's `contact` block, and a listing type's custom fields marked non-public. `pii:message` is free text people wrote: an inquiry message, and the notes and reasons staff type. An adapter *asks* in its manifest (`scopes`); the admin turns each on at `/admin/settings/adapters/<id>/`, stored as `scope_pii_contact` and `scope_pii_message` in the adapter's config; the adapter receives the intersection. One that asks for nothing sees nothing, whatever the tenant has set. Turning one on is a `tenant.settings_changed` event, so the grant is in the audit trail. |
| **Every event type is classified, and the unclassified fail closed** | `RULES` lists the dotted paths that carry personal data for each event type, `NO_PII` those reviewed and found clean (an explicit list, never derived from `ALL_EVENT_TYPES`, so a new event cannot inherit a free pass). An event in neither is withheld in full from a subscriber that does not hold both scopes. Two tests keep it honest: every `emit()`ed type must be classified, and every payload key that looks personal (email, phone, name, message, ip, notes, reason, rationale, errors) must be covered by a rule or carry a written reason in `REVIEWED_NOT_PII`. A property test fills every rule path with a sentinel and asserts none survives without its scope. |
| **JSON-patch events are redacted op by op** | `listing.updated` keeps each op and its `path` and loses the `value` of any op under `/contact`, or under a private custom field. `tenant.settings_changed` loses every op value: they are installation configuration (a mail host, a from address), and a per-tenant adapter does not receive `tenant.*` at all. A consumer still sees that something changed. |
| **Non-public custom fields are contact data** | A listing type's fields carry `public`; one marked false is the operator's private note (a license number, say) and is withheld without `pii:contact`. The drain looks the schema up per listing event and only when the scope is not held. |
| **The subscriber contract grew to match the spec** | `handle(envelope, ctx)` with an `AdapterContext` for the delivery's tenant (`None` for a `tenant.*` event). A subscriber may declare `subscribes` (glob patterns, now applied by `subscribers_for`), `scopes`, `wants(event_type, config)` and `config_key`. The fan-out consults `wants` with the adapter's own **config**, never the tenant row, so a tenant that has not configured an adapter gets no delivery rows at all; a `wants` that raises delivers anyway, since a bug in an adapter is not a reason to drop an event. |
| **One webhook endpoint per tenant in v1** | `OutboxDelivery` is unique on `(event, adapter_id)`: several endpoints would need a schema change, and one failing endpoint would re-send to the healthy ones. The URL is a **secret** (`webhook_url`), because hook URLs usually embed a token and non-secret configuration is written into `tenant.settings_changed` events. Configuration holds the host (for display and the egress check), the event patterns, `enabled` and the scope grants. `tenant.*` events and events the adapter itself originated are never sent. |
| **Signing is timestamped, a deviation from spec §8.4** | `X-OSDS-Signature: t=<unix>,v1=<hmac-sha256>` over `"<t>.<raw body>"`, keyed with a secret generated by core when the endpoint is first saved, shown once, per tenant. §8.4 signs the raw body alone with a key "rotated per install"; binding the timestamp makes a captured request useless later, and a per-tenant key means one directory's receiver cannot forge another's. Rotation is immediate (`adapter.rotate_secret`, admin only, in the command log without the value); an overlap window is a follow-up. Event ids are still the dedupe key (§8.2): delivery is at-least-once. **The spec wording is the maintainer's to amend.** |
| **Response mapping** | 2xx and 409 (duplicate) are delivered. 429 retries and carries `Retry-After`. 410 dead-letters at once. Every other 4xx, any 5xx, a redirect (never followed) and any network error retry on the drain's schedule: a misconfigured endpoint can be fixed within the twelve attempts. An egress refusal and an oversized event dead-letter at once, since neither heals. `last_error` is a status code or an error class; a response body can echo the payload and is never read into a record. The drain now records only `type(exc).__name__` for an adapter that raises. |
| **`Retry-After` is honoured as `max(backoff, hint)`, clamped to the 1h cap** | The drain used to ignore a subscriber's hint (#172 built the cap reading of §8.2). It still never retries sooner than the schedule, and never waits past the cap because a remote asked it to. #172 itself is about the *spec's* sequence wording and stays open. |
| **Egress to an operator's URL is public-only, pinned, bounded and unredirected** | The destination must be the configured host exactly. Every address it resolves to is checked, and one bad answer refuses the name. Public addresses only, unless the deployment sets `OSDS_WEBHOOK_ALLOW_PRIVATE`, which also permits plain HTTP to a private address and nothing else. **Loopback, the link-local range that holds the cloud metadata service (169.254.169.254), multicast and reserved space are unreachable whatever the setting.** The connection goes to the address that was checked with TLS verified against the hostname, so DNS cannot be rebound between check and connect. Credentials in the URL are refused, redirects are never followed, the response is capped at 64 KB, and a 25-second total deadline keeps a drip-feeding server inside the drain's 90-second claim window. |
| **Admin pages are generic and admin-only** | Built from the registered subscriber's `settings_fields()`, `scopes`, `rotatable_secrets` and `send_test`, so core never names or imports an adapter: `/admin/settings/adapters/`, the settings page, deliveries and dead letters, replay. The settings page shows the host and whether each secret is set, never the URL or a secret; a generated secret appears once, in the response that created it. "Send a test" posts a synthetic `webhook.test` envelope straight through the context and is never an outbox event. There is no auto-pause: a failing endpoint shows as failing on the list and the deliveries page. |
| **Replay refuses what retention has emptied** | `delivery.replay` (admin, in the command log) puts a dead-lettered delivery back in the queue with its attempts reset. It refuses a delivery whose event payload has been nulled (§11.2): replaying would send `{}` and call it the event. The spec's "reconstructs from current state" does not exist and is not built. Order holds: the replayed row keeps its id, so the drain's head-of-line rule holds later events for that subject behind it. |
| **The SMTP sender takes an `AdapterContext` (#215)** | `available(ctx)` and `send(ctx, MailMessage)`: plain data, never the ORM row, never the tenant. Its settings stay at `tenant.settings["smtp"]` where the wizard and the mail page write them, named by the provider's `config_key`; the password is `ctx.secret("password")`, i.e. the existing `smtp_password`. A boundary test holds everything under `adapters/` to importing `osds.adapter_api` and `osds.adapters` and no other project module. |
| **Logging (#179)** | One console handler on stdout with the secret-path mask, `osds.*` at INFO. `ctx.logger` removes every secret the adapter has resolved through `ctx.secret` before the record exists and never logs a traceback. The owner sign-in token (`/owner/signin/<token>/`) is masked in application logs and, by `osds.gunicorn_logging.MaskingLogger`, in gunicorn's access log. Every existing `osds.*` call was read: they carry ids, counts and error classes, no contact value. Core cannot scrub what it cannot recognise: keeping names and addresses out of messages stays the adapter's duty (§8.3). |
| **Known edges** | A listing event carries the operator's own listing content (name, description, address, public custom fields), which is not redacted: it is what the directory publishes. Several endpoints per tenant, overlapping secret rotation, `Retry-After` given as an HTTP date, and `ctx.kv` and `ctx.command` are not built. |

## §4.13 — Behind a TLS-terminating proxy

New subsection. #234, and the on-demand certificate check a proxy such as Caddy makes. It builds on §4.8's trust list and finishes the `SECURE_PROXY_SSL_HEADER` item that section left to its own issue.

| Decision | Reasoning |
| -------- | --------- |
| **`X-Forwarded-Proto` is believed only from a peer in `OSDS_TRUSTED_PROXIES`** | `TrustedProxyHeadersMiddleware` is the first middleware. A peer outside the list, or any peer when the list is empty, has the header deleted before anything asks `request.scheme`; the scheme is then what the server saw. `SECURE_PROXY_SSL_HEADER` stays set, and `USE_X_FORWARDED_HOST` and `USE_X_FORWARDED_PORT` are pinned off, so those headers are never read. The check is the socket peer (`REMOTE_ADDR`), never the address `client_ip()` derives from `X-Forwarded-For`. |
| **A trusted peer's header is cut to its rightmost token** | Django reads the leftmost, which is client-written when a proxy appends rather than replaces. The rightmost is the one the trusted proxy wrote, the same right-to-left rule §4.8 uses for `X-Forwarded-For`. This removes the old precondition that the proxy must strip a client-supplied header. |
| **The middleware, not gunicorn's `forwarded_allow_ips`** | gunicorn would need the trust list a second time (its default is loopback only, so a proxy in another container would silently not be trusted) or a twelfth environment variable. Its decision cannot be tested from the Django suite, it does not exist under runserver or the Windows development machine, and it does not cover a different server. The Django-level rule is one definition of trust, in `osds/client_ip.py`, with tests. |
| **One WARNING per process for a proxy missing from the list** | A private, non-loopback peer outside the list that sends `X-Forwarded-Proto` naming https is almost certainly a TLS proxy whose address was not set. Without a hint every HTTPS form POST fails the CSRF origin check as an opaque 403. Same shape as §4.8's `X-Forwarded-For` warning, and like it, a log line and not a switch. |
| **No installs exist, so the upgrade break is a README note** | An install behind a proxy with `OSDS_TRUSTED_PROXIES` unset will 403 every HTTPS POST until it is set. The README says so. Unix-socket binds have no peer address and count as untrusted; the shipped entrypoint binds TCP. On platforms where the proxy's address is not stable (Railway, Render), set a broad private CIDR. |
| **The ask endpoint is `GET /_internal/tls-ask?domain=<name>`** | The call Caddy's `on_demand_tls { ask }` makes before it requests a certificate for a name it has not seen. 200 and a body of `ok` mean yes; anything else is a bare 404. `_internal` joins `RESERVED_SLUGS` beside `_adapters`. |
| **Yes for a verified tenant domain and for the console host, and nothing else** | A tenant's `primary_domain` with `domain_verified_at` set (the predicate of `directory.routing.has_absolute_base`), or `OSDS_CONSOLE_HOST` when it is non-empty. **A suspended tenant still gets a 200**: the 503 page it serves needs HTTPS to be read, and renewals must not lapse. Changing the domain clears verification (`set_tenant_domain`), so a moved domain gets no certificate until it is verified again. The check does not wait for setup to finish, because the console host needs its certificate before the wizard does. Input is lowercased, stripped of a trailing dot, and must pass the wizard's hostname pattern, so an IP literal is refused. One indexed lookup, no cache. It reads `Tenant`, a structural model, so no tenant scope applies. |
| **It is answered inside `TenantResolutionMiddleware`, before the Host is read** | The proxy's call carries an internal Host (`osds-app:8000`) that no tenant owns, which would otherwise be an unknown-host 404 or a 400. The branch sets no urlconf and no tenant scope. The middleware stays the one host gate. No event, no command-log row and no access-log row: it changes nothing and shows no tenant data. |
| **Refused by falling through, not by a 403** | The branch fires only when the socket peer is in `OSDS_TRUSTED_PROXIES` **and** the request carries no forwarding header (`X-Forwarded-For`, `-Host`, `-Proto`, `-Port`, `Forwarded`, `X-Real-IP`). Anyone else, including every request when the list is empty, gets exactly what any unknown path gets, so the path does not reveal itself. Public traffic a proxy relays always carries a forwarding header and the proxy's own ask call never does, so a visitor cannot reach the endpoint through the proxy. A proxy that adds no forwarding headers defeats that, which is why the proxy duty below exists. With the list empty the endpoint is dark and the proxy issues nothing: it fails closed. No shared secret and no new environment variable. |
| **What a proxy must do** | (1) Sit inside `OSDS_TRUSTED_PROXIES`. (2) Answer 404 for `/_internal/*` on its public listener. (3) Serve `/.well-known/osds-challenge` over plain HTTP **without redirecting it to HTTPS**. Domain verification fetches that URL over HTTP and follows redirects (`tenants/dns_check.py`); a proxy that redirects sends it to a TLS handshake that needs a certificate, which the ask endpoint refuses because the domain is not yet verified, so verification could never succeed. |
| **Deployment** | The default compose file stays three containers plus the media volume, and this change adds none. An opt-in `docker-compose.tls.yml` with Caddy ships later as the documented VPS recipe, in its own PR. There is no in-app ACME for the alpha. This is not the fifth-container question of §3: the default install is unchanged. |
| **Known edges** | An IPv6 or IDN domain must be given in its ASCII form (the wizard enforces it). A relayed request through a proxy that sends no forwarding headers can reach the endpoint and learn whether a name is a verified tenant domain; that is already public in certificate-transparency logs. Spec §13 says nothing about TLS termination and still lists `minio`; that is a spec edit and is raised separately. |
| **The Caddy recipe shipped: pinned image, fixed subnet, trust one address** | `docker-compose.tls.yml` and `Caddyfile` (this ships what the Deployment row said was coming). Image `caddy:2.11.6`, an exact tag: an upgrade is an edit, not a pull. The overlay replaces the default network with `172.28.77.0/24`, pins Caddy at `172.28.77.10` and limits unpinned containers to `172.28.77.128/25`, so none can take Caddy's address first. `OSDS_TRUSTED_PROXIES` is that one address, not the subnet: only Caddy is believed. The range sits outside Docker's default pools to avoid colliding with them; if it collides with a network on the host, change the subnet, `ip_range`, `ipv4_address` and `OSDS_TRUSTED_PROXIES` together. `OSDS_CONSOLE_HOST` is required (`:?`) in the overlay instead of defaulting to `localhost`, because the ask endpoint refuses a single-label name and no certificate would ever be issued. `ports: !reset []` unpublishes the app and needs Compose 2.24 or later. The Caddyfile is untested against `localhost` for that reason; the smoke test used `osds.localhost` with `local_certs` added to a scratch copy only. |

## 5. Working conventions

- Branch, PR, squash-merge. Never commit to `main` — branch protection refuses it.
- `git commit -s` always. DCO is required by `CONTRIBUTING.md`.
- Conventional Commits. One concern per PR.
- `python manage.py check` and `python manage.py test` before opening a PR.
- `gh issue create` takes `--label`; labels are not applied otherwise, and a nonexistent label fails the whole command.
- Windows / PowerShell 7. Here-strings for file creation — `>` produces UTF-16 and breaks everything downstream.
- Migrations are forward-only. **A recorded migration is never edited.** A correction is a new forward migration, written to be idempotent so a from-zero database is unaffected. CI cannot catch an edited migration — it migrates from zero on every run, so an edited migration and a correct one are indistinguishable.
- `git checkout main; git pull` before every `git checkout -b`.
- Every entitlement state transition needs a test. That table is where this system rots if it rots.

### Prompting Claude Code

Prompts must be short — long ones fail to paste. Give it the task, the spec
section, and the constraint; let it read the rest.

**Ask "report, do not change" before accepting any layer that touches roles,
locks, or event emission.** Three real bugs in the Node build — a phantom
patch operation, a missing row lock, and a persistence layer that silently
required the database owner role — all surfaced from narrow read-only
questions, not from reviewing the diff. None would have been caught by a green
test run.

**When it flags a deviation from the spec, take it seriously.** It was right
six times in the Node build where the spec or the instruction was wrong, and it
correctly refuses to invent event names not present in the spec.

**Push back on generated bulk-rewrite scripts.** When it proposed a regex
rewrite of imports across 25 files, the right answer was to fix the compiler
setting so each site was identified individually.

**Numbers in a completion report are counted or omitted.** It reported "263
tests passing" and "30 new tests" in the same sentence with the same
confidence; the first was counted and correct, the second was estimated and
wrong by seven. Ask for the count command, not the number.

**A green suite cannot see cookie flags.** The Django test Client ignores
`Secure` and never sets `wsgi.url_scheme='https'`. Anything touching cookie
security is verified with a raw HTTP request against a non-loopback host, or
it is not verified.

**Unit tests that mock the database will not catch a missing table.** Run the
browser pass.

**A view gate is not a template gate.** `import_rollback` was manager-gated
while its template's `can_rollback` had no role term, so an editor saw a
button the view would 403. The role test varied batch state only. Green
suite; visible in five seconds in a browser.

**A test that reads an env var at import can pass in CI and fail locally on
the same commit.** #202. `OSDS_SECURE_COOKIES` must be `true` for the suite
and `false` for a plain-HTTP browser pass, and the two cannot share a
terminal.

Approve reads individually. Do not whitelist `git push`, `git add *`,
`docker exec *`, or anything that writes outside the repository.
